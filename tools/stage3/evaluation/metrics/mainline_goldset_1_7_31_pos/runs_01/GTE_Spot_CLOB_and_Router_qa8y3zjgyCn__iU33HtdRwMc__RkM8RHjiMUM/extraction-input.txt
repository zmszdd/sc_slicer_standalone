Expired Orders Cannot Be Revived by Extending `cancelTimestamp` When Only the Amount is Amended

## Finding description and impact

**Description**

According to the project team, it is intended behavior that an expired order can be "revived" by amending it with a new, future `cancelTimestamp`. This functionality works as expected when the order's `price` or `side` is changed, as this flow is handled by `_executeAmendNewOrder`, which re-creates the order with all new parameters, including the new `cancelTimestamp`.

However, if a user attempts to revive an expired order by only changing its `amountInBase` (and providing a new `cancelTimestamp`), the amendment is processed by `_executeAmendAmount`. This function only updates the order's `amount` and does not update the `cancelTimestamp`.


As a result, the expired order remains expired on the books. While it is not immediately canceled, it is effectively unusable and will be automatically removed and refunded the next time it is encountered during the matching process, failing to achieve the user's and the protocol's intended outcome of reviving the order.

**Impact**

This is a functional bug that leads to inconsistent behavior and breaks a core design intention of the protocol. Users who try to revive an expired order by adjusting its size will find their transaction succeeds, but the order remains expired and non-functional. 

---

## Recommended mitigation steps

To ensure consistent behavior and align with the protocol's intent, the `cancelTimestamp` should be updated in all amendment scenarios.

In the `_processAmend` function, before branching into `_executeAmendNewOrder` or `_executeAmendAmount`, unconditionally update the `order.cancelTimestamp`.

Alternatively, add `order.cancelTimestamp = uint32(args.cancelTimestamp);` inside the `_executeAmendAmount` function.
