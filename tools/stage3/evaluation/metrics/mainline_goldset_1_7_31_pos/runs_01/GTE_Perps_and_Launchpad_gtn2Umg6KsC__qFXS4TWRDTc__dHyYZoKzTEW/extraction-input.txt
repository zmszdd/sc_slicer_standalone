Token–pair mismatch in Distributor.addRewards lets anyone brick quote payouts (per-pool DoS)

## Summary

An attacker can call:


addRewards finds the pool via launchAsset but never checks that token1 == rs.quoteAsset. It:
* calls rs.addQuoteRewards(launchAsset, fakeToken, X)
* credits totalPendingRewards[fakeToken] += X
* pulls fakeToken via transferFrom

Internally, the pool accrues quote pending for users. Later, claimRewards(launchAsset) tries to pay out the real quote token and calls:


This underflows (totalPendingRewards[realQuote] == 0) → ClaimAmountExceedsTotalPendingRewards() → DoS for all quote claims on that pool.

## Affected code

* contracts/launchpad/Distributor.sol — addRewards(...) selects the pool by token0/token1 but never enforces that the “other” token equals rs.quoteAsset; it then credits pending under the attacker-supplied token and transfers that token in.
* contracts/launchpad/Distributor.sol — _decreaseTotalPending(quote, amount) reverts when user later claims real quote rewards because totalPendingRewards[realQuote] wasn’t credited.

## Root cause
* Missing invariant: the token pair passed into addRewards is not validated to match the established {launchAsset, rs.quoteAsset} pair. As a result, external input decides which token key is used for both totalPendingRewards[...] and the incoming transfer.

## Impact

* Per-pool permanent DoS of quote reward claims (until a migration/upgrade).
* Funds accounting becomes inconsistent: users see positive pendingQuote but the distributor has pending tracked under a different token key.

## Attack / trigger scenario

1. Pool exists and has totalShares > 0.
2. Attacker deploys fakeToken and approves the Distributor.
3. Calls addRewards(launchAsset, fakeToken, 0, X).
4. Users now have pendingQuote > 0 internally, but totalPendingRewards[realQuote] == 0 and totalPendingRewards[fakeToken] == X.
5. Any claimRewards(launchAsset) reverts with ClaimAmountExceedsTotalPendingRewards.
