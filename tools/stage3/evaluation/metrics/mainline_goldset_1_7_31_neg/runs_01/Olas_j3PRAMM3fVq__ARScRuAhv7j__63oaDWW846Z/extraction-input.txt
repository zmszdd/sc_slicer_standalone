Another operator address can be used as instance address to permanently block the operator from registering agent instances

## Finding description
*Note: I already submitted this report without knowing that `ServiceRegistry` is out of scope and the report targets both the registry and the manager. So in order not to mark the finding as out of scope while it is still valid, I sacrificed another finding slot and rewrite the finding to make it 100% target the `ServiceManager`*

Neither the `ServiceManager.registerAgents` nor `ServiceRegistry.registerAgents` functions check whether the given instances addresses are already in use as operator address. So if a malicious operator uses another operator's address as an instance address while registering agent instances for a service, it will permanently block the other operator from registering any agent instance for any service in the future.


An attacker can create a service with many slots just for this purpose. This attack cannot be stopped by pausing the `ServiceManager` as there is not pause check in the `ServiceManager.registerAgents` function.

The operator whitelist too is not helpful in this case as it is per service not global. So if the attacker creates his service, the whitelist won't help. The service can be created without the intention to push it to deploy but only to keep it at `ActiveRegistration` state just to be able to register instances and DOS other operators.

The DOS'ed operators cannot unbond themselves because the service state is not `TerminatedBonded`. Even if the state is `TerminatedBonded`, the operator has not registered agent instance because his address is used as an instance not as an operator. So the unbond call will revert.

The DOS'ed operators can use another address but this will make managing instances harder for the operators. Plus the design supports registration of multiple/unlimited instances per operator for different services so this feature will be broken. Even worse, the malicious operator can keep registering any new operator address to ensure the DOS.

Also, using many addresses by operators (note that this is an unlimited many due to possibility of continuous DOS of the other addresses) will make management very hard for operators. Because the registered address is the receiver of staking rewards and the sender of registration fees. So using many address will lead to fragmentation of the operator funds.

There are currently operators onchain using same address to register agent instances.

## Impact
- Any operator can use any other operator's address as an instance address while registering agent instances for a service. This will permanently block the other operator from registering any agent instance for any service in the future, resulting in a Denial of Service (DoS) attack.
- The feature where an operator can register instances for many services with the same address is broken.

## Mitigation
Add a mapping in `ServiceManager` contract to keep track of all operator addresses so that it will be checked when calling `ServiceManager.registerAgents` if any of the provided instances address is already an operator address. At the end of the function (meaning registration successful), add the operator address to the mapping by mapping it with the number of registered instances. During `ServiceManager.unbond`, reduce the mapped number of registered instances so that when 0, the address can be used as an instance address later.
