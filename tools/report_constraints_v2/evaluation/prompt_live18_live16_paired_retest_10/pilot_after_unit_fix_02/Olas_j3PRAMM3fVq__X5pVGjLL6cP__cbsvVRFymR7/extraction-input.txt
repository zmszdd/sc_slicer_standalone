StakingNativeToken._withdraw() Balance Corruption via Reentrancy Causes Contract Insolvency and DoS for All Stakers

## Finding description and impact

The `_withdraw()` function in `StakingBase` (lines 929-948) reads the `balance` state variable into a local variable at the start, makes multiple external ETH transfers in a loop via `_transfer()`, and only writes the updated balance back to storage **after all transfers complete**. For `StakingNativeToken`, each `_transfer()` call sends ETH via `to.call{value: amount}("")` (line 29), giving execution control to the recipient.

**Vulnerable code in StakingBase.sol (lines 929-948):**

**StakingNativeToken._transfer() (lines 27-33) sends ETH:**

If a reward recipient re-enters the staking contract during `_transfer()` (e.g., by calling `claim()` for a **different** service they own), the inner `_withdraw()` reads the **stale** `balance` from storage (outer hasn't written yet). When the outer `_withdraw()` resumes, it **overwrites** the inner write with its own stale local variable, permanently corrupting the `balance` accounting.

**Attack scenario:**

1. Attacker owns two services (A and B), both staked in the same `StakingNativeToken` contract. Both use `RewardDistributionType.ServiceOwner`. Contract `balance = 100 ETH`.

2. Attacker calls `unstake(serviceA)` which triggers `_withdraw()`:
   - **Outer `_withdraw()`**: reads `updatedBalance = 100` from storage.
   - `updatedBalance -= 5` → local `updatedBalance = 95`.
   - `_transfer(attacker, 5 ETH)` sends ETH to attacker's contract.

3. **Attacker's `receive()` triggers**, calling `claim(serviceB)`:
   - **Inner `_withdraw()`**: reads `updatedBalance = 100` from storage (**STALE!**).
   - `updatedBalance -= 5` → inner local `updatedBalance = 95`.
   - `_transfer(victim, 5 ETH)` sends 5 ETH.
   - **Inner writes `balance = 95`** to storage.

4. **Outer `_withdraw()` resumes**:
   - Writes **`balance = 95`** to storage (its own stale local).
   - **Overwrites** the inner write.

5. **Result**:
   - Contract sent out **10 ETH** total (5 + 5).
   - But `balance = 95` instead of correct `90`.
   - **Contract is insolvent**: recorded balance > actual ETH.
   - All remaining stakers who try to withdraw amounts that exceed actual ETH will be permanently DoS'd.

**Note on reentrancy guard**: Neither `_claim()`, `_unstake()`, `_withdraw()`, nor `_stake()` have reentrancy guards. The comment on line 564 says "the reentrancy is not possible since the reward is set to zero" — but this only prevents re-claiming the **same** service. Claiming a **different** service owned by the same attacker is not prevented.
