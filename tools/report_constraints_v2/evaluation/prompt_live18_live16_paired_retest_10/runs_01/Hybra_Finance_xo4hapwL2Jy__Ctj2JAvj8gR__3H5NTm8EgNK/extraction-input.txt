Dynamic Fee Mechanism Broken by Conflicting Fee Caps

## Finding description and impact

The dynamic fee system contains a cconflicting fee caps between `DynamicSwapFeeModule.getFee()` and `CLFactory.getSwapFee()` which renders the dynamic fee mechanism ineffective. The `DynamicSwapFeeModule` allows fees up to 500,000 (50%) internally, but `CLFactory.getSwapFee()` rejects any fee above 100,000 (10%), causing the system to always fall back to basic tick spacing fees.


We can see in DynamicSwapFeeModule that the MAX_FEE_CAP is set to 500,000.


And in CLFactory the getSwapFee function rejects any fee above 100,000 (10%), upon which it falls back to the default tick spacing fee.


As a result, any dynamically calculated fee above 10% gets rejected reducing potential protocol revenue. Potential user discounts applied in `getFee()` are lost when the factory rejects the final fee. And the 50% anti-MEV protection cap becomes unusable, leaving pools vulnerable to maximal extractable value attacks during high volatility

## Recommended mitigation steps


Align `getSwapFee` threshold with `MAX_FEE_CAP` (500_000) to allow full dynamic fees. Otherwise, fallback to 100_000 (10%) fee instead for swaps.
