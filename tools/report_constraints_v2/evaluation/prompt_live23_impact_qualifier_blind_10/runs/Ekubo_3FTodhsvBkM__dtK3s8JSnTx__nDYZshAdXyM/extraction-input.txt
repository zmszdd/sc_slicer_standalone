Lack of Slippage Protection in `Positions.deposit` Allows Excessive Token Deduction via Extension Execution

## Finding description and impact

### Root Cause

The vulnerability lies in the `deposit` function of `BasePositions.sol`. This function calculates the liquidity to mint based on the pool's *current* price (before any state changes) and the user's provided `maxAmount0` and `maxAmount1` constraints.

It then calls `CORE.updatePosition` with this calculated liquidity. However, `CORE.updatePosition` triggers the `beforeUpdatePosition` hook on any registered extension (such as TWAMM) *before* executing the liquidity addition logic.

If the extension executes logic that changes the pool's price (e.g., executing pending virtual orders in TWAMM), the state of the pool shifts significantly between the initial check and the final execution. When `CORE` resumes the `updatePosition` logic, it recalculates the token amounts required for the *previously calculated liquidity* based on the *new* price.

Because `deposit` does not re-verify the final deducted amounts against `maxAmount0` and `maxAmount1` after the `lock` callback returns, the user can be charged amounts that exceed their specified limits.

### Impact

Users can be forced to pay significantly more tokens than they authorized. This effectively bypasses the slippage protection that `maxAmount` arguments are intended to provide.

In a TWAMM pool, if a user deposits liquidity after a period of inactivity (or is sandwiched by a MEV bot triggering the TWAMM execution), the accumulated price impact from virtual orders will apply *during* their deposit transaction. This can shift the price unfavorably, causing the protocol to deduct more of the depreciated token to maintain the requested liquidity, directly violating the user's authorized maximums.
