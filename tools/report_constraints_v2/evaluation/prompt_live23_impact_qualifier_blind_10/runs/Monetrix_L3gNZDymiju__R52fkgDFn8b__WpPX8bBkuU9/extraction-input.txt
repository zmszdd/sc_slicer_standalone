Full BLP unwind does not retire 0x811 supplied-slot registry, causing global Accountant DoS

## Summary

The function `MonetrixVault.supplyToBlp()`


 automatically registers a Vault-side 0x811 supplied slot in `MonetrixAccountant.vaultSupplied`.


but `MonetrixVault.withdrawFromBlp()`

 never removes that registry entry when the BLP position is fully unwound. MonetrixAccountant.totalBackingSigned()


 later iterates every registered supplied slot and performs a strict `PrecompileReader.suppliedBalance()` read


 which **reverts** if the external 0x811 slot is absent or unreadable. As a result, after a normal BLP supply-then-full-withdraw lifecycle, the protocol can enter a state where `totalBackingSigned()`, `surplus()`, `distributableSurplus()`, and `settle()` all revert until a separate manual `removeSuppliedEntry()` cleanup is performed. Essentially a cosmic DoS leading to a lifecycle-coupling and accounting-liveness bug, not a theft bug.

### There was a quick peform RPC call test and it returns 


So the real RPC did not return a normal zero-filled payload for the absent 0x811 slot. It errored.

That is why, in the PoC, modeling the missing slot as an unreadable/reverting PRECOMPILE_SUPPLIED_BALANCE call is consistent with what we observed on the live RPC.


# Impact

- Uses a normal supported BLP lifecycle: supply, then withdraw max/full unwind
- Not a theft bug and not bad-parameter misuse
- Root cause is incomplete lifecycle coupling between registry registration and registry retirement
- Impact is protocol-wide accounting and settlement liveness failure


# Note to the Judge and Sponsor

The issue resides in a Operator side vector and perfectly fits the 2 categories mentioned in the contest details:

### Areas of concern (where to focus for bugs)

1. Accountant 4-gate settle pipeline
2. HyperCore precompile read semantics.

The issue its **NOT** about the operator theft or trusting the operator because of funds or other inputs, the issue **its a lifecycle bug** that directly breaks the Monetrix accounting state, in a obviously vector where the operator usually peforms actions. 

So the bug lives in an Operator vector area, but the flaw is still a protocol lifecycle/invariant bug, not a trust-minimization complaint. That is consistent with the sponsor calling out the Accountant settle pipeline and HyperCore precompile semantics as areas of concern.

Technically. Monetrix models BLP-supplied assets as a registered external resource, but its lifecycle is asymmetric: the resource is auto-registered when created and not auto-unregistered when destroyed, so strict Accountant reads can keep treating a dead `0x811` slot as mandatory and brick global accounting.

in short this is a lifecycle/accounting bug, not an operator theft/inactivity bug
