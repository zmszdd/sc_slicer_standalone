GaugeManager._createGauge() Blindly Accepts Any Contract as CL Pool (isPair=true) Without Factory Validation, Allowing Emission Theft via Fake Gauges

## Finding description and impact

Root Cause
The ```GaugeManager._createGauge()``` function implements asymmetric validation between V2 and CL pool types. For V2 pools ```(_gaugeType == 0)```, it correctly validates pool legitimacy via ```IPairFactory(_factory).isPair(_pool)```, ensuring only factory-registered pools can receive gauges. However, for CL pools ```(_gaugeType == 1)```, the validation was removed (commented out due to code size constraints) and replaced with ```isPair = true```, unconditionally accepting any contract as a valid CL pool.
The commented-out check require(_pool_hyper == _pool_factory, 'wrong tokens') only validated token addresses match, not that the pool exists in ```ICLPoolFactory```. The current implementation performs token whitelist checks via ```TokenHandler.isWhitelisted()```, but this validates tokens themselves, not pool contract legitimacy. An attacker can deploy a fake pool contract returning whitelisted tokens from ```token0()/token1()``` while maintaining complete control over the pool's internal logic.
## Impact
 Complete Protocol Emission Theft:

Attacker deploys fake CL pool contract using whitelisted tokens (HYBR/rHYBR)
Calls createGauge() to obtain official gauge for fake pool (bypasses all validation)
Acquires veNFT voting power and votes 100% weight to attacker's gauge
Each epoch, minted emissions flow to attacker-controlled gauge
Attacker extracts funds by creating fake LP positions in their controlled pool contract
