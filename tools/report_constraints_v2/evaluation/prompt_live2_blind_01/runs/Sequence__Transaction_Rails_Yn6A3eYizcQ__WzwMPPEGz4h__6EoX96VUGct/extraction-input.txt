Signature Validation Permanently Bricked by Stale chainid in `DOMAIN_SEPARATOR`

## Finding description and impact

The EIP-712 `DOMAIN_SEPARATOR` is a critical security mechanism designed to prevent a signature created for one protocol from being re-used on another. It achieves this by creating a unique fingerprint for the contract.

In implementation, the `DOMAIN_SEPARATOR` is calculated in the constructor and stored as an immutable variable. This calculation permanently captures and hard-codes the `block.chainid` that was present at the time of deployment.

However, the `_verifyAndMarkIntent` function uses live `chainid()` when calculating the separate `intentHash`.

[**Code Snippet**](https://github.com/code-423n4/2025-11-sequence/blob/593987c2b569f3212d2cadb31fc8d14b84bc30a9/src/TrailsIntentEntrypoint.sol#L65)

If the network undergoes a hard fork or an L2 upgrade that changes its `chainid`, a significant mismatch occurs. The contract attempts to validate the signature by calculating a `digest` from two conflicting data sources:

a) The `DOMAIN_SEPARATOR`, which is stale and hard-coded with the old `chainid` from its immutable slot.

b) The `intentHash`, which is calculated live using the new `chainid()` opcode.

The `digest` calculated by the contract (using a mix of old and new chain IDs) will never match the digest signed by the user (using only the new chain ID). As a result, `ECDSA.recover` will always fail, and the `InvalidIntentSignature` error will be triggered on every call. This permanently bricks both `depositToIntent` and `depositToIntentWithPermit`, leading to a total Denial of Service (DoS) for the protocol. Given the system uses multiple chains and the contract is non-upgradeable, the high likelihood of future chain ID changes combined with the impact of a permanent DoS results in a Medium severity.
