sUSDM breaks ERC-4626 decimals invariants (_decimalsOffset vs decimals)

## Summary
sUSDM implements ERC-4626 with a non-zero _decimalsOffset() but overrides decimals() to an inconsistent value, causing share-unit mismatches between ERC-4626 math and what integrators/users think the share token decimals are. This can lead to incorrect pricing/quotes, wrong UI display, and unsafe integration behavior for any system relying on ERC-4626 semantics.

## Affected code
1. src/tokens/sUSDM.sol
- _decimalsOffset() returns 6
- decimals() is overridden to return 6

Under OpenZeppelin ERC-4626, the vault’s decimals should be:
vaultDecimals=assetDecimals+_decimalsOffset()
USDM uses 6 decimals, so with _decimalsOffset() = 6, ERC-4626 expects sUSDM.decimals() to be 12.

## Issue details
In OZ ERC-4626 v5.x, the conversion functions rely on _decimalsOffset():

- _convertToShares uses totalSupply() + 10**_decimalsOffset()
- _convertToAssets uses totalSupply() + 10**_decimalsOffset()
So the contract’s internal accounting is explicitly configured for a +6 decimals offset (virtual shares model), but at the same time the token reports only 6 decimals via decimals().

This creates a semantic inconsistency:

- On-chain ERC-4626 math behaves as though shares have 12-decimal scaling vs the underlying.

- Off-chain and integrator assumptions (wallets, indexers, routers, vault aggregators, price/oracle adapters) will treat shares as 6 decimals and may scale values incorrectly.

## Impact
1. Incorrect share pricing / quoting: integrators computing price-per-share, exchange rates, or minOut/maxIn using share decimals can produce incorrect values.

2. Unsafe integration behavior: vault routers and aggregators may pass wrongly-scaled amounts (especially in systems that normalize to 18 or to decimals()), potentially causing:
- deposits/mints failing unexpectedly,
- wrong slippage protections,
- misleading UI amounts that cause users to sign transactions they don’t intend.
3. Accounting/reporting drift: dashboards and off-chain accounting that rely on decimals() to format shares can misreport balances and APY.

Even if core protocol flows “work” in isolation, this is a high-severity integration correctness bug for an ERC-4626 share token.

## Proof / reasoning
1. sUSDM._decimalsOffset() returns 6, enabling the OZ ERC-4626 “virtual shares” mechanism at 10**6.

2. OZ ERC-4626 defines decimals() as underlyingDecimals + _decimalsOffset().
3. sUSDM.decimals() is overridden to always return 6, contradicting the ERC-4626 implementation assumptions.
