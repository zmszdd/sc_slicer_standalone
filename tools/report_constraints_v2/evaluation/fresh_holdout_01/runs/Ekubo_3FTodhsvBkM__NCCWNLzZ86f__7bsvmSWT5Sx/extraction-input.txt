Arbitrary Debt Forgery via updateDebt Reentrancy Enables Free Swaps and Pool Reserve Drainage

## Summary

FlashAccountant.updateDebt() allows any address to modify the current locker's debt during an active lock, using msg.sender as the token address with no access control. A malicious ERC20 token can reenter updateDebt() during transferFrom() to zero out its owed input debt, while Router withdraws output tokens before payment settlement. This enables complete pool reserve drainage as attackers receive output tokens without paying input tokens.

## Vulnerability Details

### Root Cause

The vulnerability exists in FlashAccountant.updateDebt() at lines 132-143 of `src/base/FlashAccountant.sol`:


The function uses `msg.sender` as the token address with no validation. The only check is `_getLocker()`, which verifies an active lock exists but does not verify that `msg.sender` is authorized to modify debt for that token address. This allows any contract, including malicious ERC20 tokens, to arbitrarily modify debt during a lock.

### Affected Contracts

- **FlashAccountant.sol**: Contains the vulnerable `updateDebt()` function and `_accountDebt()` implementation
- **FlashAccountantLib.sol**: Contains `payFrom()` which calls `transferFrom()`, providing the reentrancy entry point
- **Router.sol**: Handles swap settlement by withdrawing output tokens before calling `payFrom()` for input tokens
- **Core.sol**: Updates debt during swaps via `_updatePairDebtWithNative()` at line 834

The contracts interact through the lock mechanism: Router acquires a lock, Core.swap updates debt, Router settles by withdrawing outputs then paying inputs, and the malicious token reenters during payment to manipulate debt.

### How Debt Forgery Works

The attack exploits the settlement order in Router.handleLockData() combined with reentrancy during token transfers.

**Step 1: Debt Creation During Swap**

When Core.swap executes at line 834, it calls `_updatePairDebtWithNative()` which sets:
- `debt[lockerId][inputToken] = +amountIn` (positive means locker owes this amount)
- `debt[lockerId][outputToken] = -amountOut` (negative means locker receives this amount)

**Step 2: Router Settlement Order**

Router.handleLockData() at lines 121-127 (for price-increasing swaps) or 128-146 (for price-decreasing swaps) settles debts in this order:

1. First: `ACCOUNTANT.withdraw(outputToken, recipient, amountOut)` - transfers output token to attacker
2. Second: `ACCOUNTANT.payFrom(swapper, inputToken, amountIn)` - attempts to pull input token from attacker

**Step 3: Reentrancy During Payment**

FlashAccountantLib.payFrom() at lines 52-83 calls `token.transferFrom()` at line 67. A malicious token's `transferFrom()` hook can reenter and call:


This sets `debt[lockerId][inputToken] = +amountIn + (-amountIn) = 0`, zeroing the input debt.

**Step 4: Lock Completion**

When the lock exits at lines 175-181 of FlashAccountant.sol, it checks `NONZERO_DEBT_COUNT`. After the manipulation:
- Input token debt: 0 (zeroed by reentrancy)
- Output token debt: 0 (consumed by withdraw)

The lock succeeds, and the attacker keeps the output tokens without paying input tokens.

### Attack Flow

1. Attacker deploys malicious ERC20 token (TokenM) with a `transferFrom()` hook that calls `Core.updateDebt(int128(-amount))` during transfers
2. Attacker creates a pool with TokenM and a legitimate token (TokenA), adding liquidity
3. Attacker calls `Router.swap()` with TokenM as input, requesting exact input swap
4. Router.lock() acquires a lock and calls Router.handleLockData()
5. Router._swap() calls Core.swap(), which executes the swap and updates debt:
   - `debt[lockerId][TokenM] = +100` (attacker owes 100 TokenM)
   - `debt[lockerId][TokenA] = -50` (attacker receives 50 TokenA)
6. Router.handleLockData() withdraws TokenA to attacker: `ACCOUNTANT.withdraw(TokenA, attacker, 50)`
   - This sets `debt[lockerId][TokenA] = -50 + 50 = 0`
7. Router.handleLockData() attempts payment: `ACCOUNTANT.payFrom(attacker, TokenM, 100)`
8. FlashAccountantLib.payFrom() calls `TokenM.transferFrom(attacker, ACCOUNTANT, 100)`
9. TokenM's `transferFrom()` hook reenters: `Core.updateDebt(int128(-100))`
10. FlashAccountant.updateDebt() sets `debt[lockerId][TokenM] = +100 + (-100) = 0`
11. `transferFrom()` completes (may transfer 0 tokens or revert, doesn't matter)
12. FlashAccountantLib.completePayments() credits payment (amount is 0 due to manipulation)
13. Lock exits successfully: all debts are zero, `NONZERO_DEBT_COUNT = 0`
14. Result: Attacker received 50 TokenA, paid 0 TokenM, pool lost 50 TokenA reserves

### Impact

**Direct Financial Loss**: Complete drainage of counterpart token reserves from any pool containing the malicious token. An attacker can repeatedly execute swaps, extracting all reserves of the paired token without providing any input tokens. For a pool with $1M in TokenA reserves paired with TokenM, the attacker can drain the entire $1M.

**Systemic Risks**: 
- All pools containing the malicious token become insolvent
- Liquidity providers lose all funds in affected pools
- Protocol fee reserves can be drained if fees accumulate in vulnerable pools
- Cascading failures as pools are systematically drained

**Affected Operations**:
- Router.swap() - enables free swaps draining pool reserves
- Positions.deposit() - enables free liquidity deposits (if malicious token is used)
- Any operation using payFrom() with the malicious token

**User Impact**:
- Liquidity providers lose all funds in pools containing malicious tokens
- Users cannot trade through affected pools (pools become empty)
- Downstream protocols integrating Ekubo routing receive incorrect pricing
- Protocol reputation damage from systematic fund drainage

**Attack Cost**: Minimal - only gas costs (~200k-500k gas per swap) and initial liquidity to create the pool. The attack scales linearly with pool reserves.

**Detection**: On-chain monitoring can detect abnormal patterns: successful swaps with no corresponding input token transfers, pools losing reserves without matching inflows, and ERC20 contracts calling updateDebt() during transfers.

**Recovery**: Requires immediate protocol pause and contract upgrade. No on-chain recovery mechanism exists. Affected pools cannot recover without external intervention.
