Permit Front-Running depositToIntentWithPermit Enables a Denial of Service Griefing Attack

## Summary

A vulnerability exists in the `depositToIntentWithPermit` function, which allows an attacker to front-run a user's transaction and cause it to fail, resulting in wasted gas. The function calls `IERC20Permit.permit()` directly, which is a well-known anti-pattern.

An attacker can monitor the mempool for a `depositToIntentWithPermit` transaction, extract the valid `permit` signature, and submit a separate transaction that *only* calls `permit()` with a higher gas fee. This front-run transaction will succeed, consuming the permit's nonce.

When the user's original, legitimate transaction is mined, its call to `permit()` will fail (as the nonce is already used), causing the entire transaction to revert. This is a classic DoS/griefing attack that forces the user's transaction to fail, wastes their gas, and permanently blocks them from using that specific `WithPermit` transaction, forcing them into a less efficient recovery flow.

## Vulnerable Code

The vulnerability is in the `depositToIntentWithPermit` function, specifically the direct call to `permit()` which is not wrapped in a `try/catch` block.


## Impact

This flaw allows an attacker to conduct a griefing attack, impacting the protocol's availability for a user:

1. **Attack:** An attacker sees a user's `depositToIntentWithPermit` transaction in the mempool. They copy the permit signature and parameters.
2. **Front-run:** The attacker broadcasts a transaction that *only* calls `IERC20Permit(token).permit(...)` with the stolen signature and a higher gas fee.
3. **Attacker's Tx Succeeds:** The attacker's transaction is mined first, granting the `TrailsIntentEntrypoint` contract the required allowance and consuming the permit's nonce.
4. **User's Tx Fails:** The user's original transaction is mined next. `_verifyAndMarkIntent` passes, but the `IERC20Permit(token).permit(...)` call reverts because its nonce has already been used.
5. **Complete Transaction Revert:** Because the `permit()` call reverted, the **entire transaction reverts** due to Solidity's atomicity guarantees. All state changes from `_verifyAndMarkIntent` (the `nonce` increment and `usedIntents` update) are rolled back.
6. **The Result:** Because all state changes are rolled back, the user's intent remains unconsumed and the nonce is not incremented. However, their transaction has **failed, and they have wasted gas**. More critically, the attacker has already consumed their permit signature by successfully executing it first. The user cannot simply retry the same transaction because the permit signature has been used. They must either:
   - Create a new intent with a new signature and permit (which can be front-run again), or
   - Switch to using `depositToIntent` (which requires a separate approval transaction, making it less gas-efficient)

This attack can be repeated indefinitely on every new `WithPermit` attempt, forcing the user to waste gas repeatedly or abandon the permit-based flow entirely.
