`ProgressiveCurve` / `OffsetProgressiveCurve` — `previewWithdraw` reverts due to mixed rounding causing underflow

## Vulnerability details

### Impact

The `previewWithdraw` function in both `ProgressiveCurve` and `OffsetProgressiveCurve` uses mixed rounding directions that can cause an arithmetic underflow revert. Specifically:

- `deduct = PCMath.divUp(wrap(assets), HALF_SLOPE)` rounds **up**
- `PCMath.square(s)` rounds **down** (via standard `mul`)

When a user attempts to withdraw an amount close to `totalAssets`, the rounded-up `deduct` value can exceed the rounded-down `square(s)`, causing `sub(PCMath.square(s), deduct)` to underflow and revert.

This is notable because the differential change area (README focus: lines 240/247) fixed `_convertToAssets` (the redeem path) to use consistent round-down arithmetic via `PCMath.square` on both terms. However, `previewWithdraw` was **not** updated with the same consistency and still mixes `divUp` with `square` (round-down).

**Concrete impact:**
- Users who attempt to withdraw all or nearly all assets from a vault using `previewWithdraw` can experience unexpected reverts
- This affects the MultiVault's withdrawal flow since it calls `previewWithdraw` to determine how many shares to burn for a given asset withdrawal
- The issue is most pronounced with small slopes or when `totalAssets` and `totalShares` are at values where the 1-wei rounding difference between `divUp` and `square` matters
