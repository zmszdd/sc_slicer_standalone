Cross-Service Reentrancy in StakingBase::_withdraw Allows Balance Accounting Corruption Leading to Protocol Insolvency

## Finding description and impact

A missing reentrancy guard in `_withdraw()` will cause **balance accounting corruption** for **the staking contract and all future stakers** as **a malicious service owner** will **re-enter during ETH transfer to unstake multiple services, causing only one balance decrement to persist while extracting rewards for all services**.

| :--- | :--- |

| **Vector** | Reentrancy via ETH transfer callback during `unstake()` |

| **PoC File** | `test/StakingBaseReentrancyPOC.t.sol` |

A malicious, unprivileged external attacker can corrupt the protocol's balance accounting by exploiting a reentrancy vulnerability in [StakingBase::_withdraw()](https://github.com/valory-xyz/autonolas-registries/blob/be1057a5e37f17f26b13c41311fe0e8e40259484/contracts/staking/StakingBase.sol#L929-L948). The vulnerability allows the attacker to break the core accounting invariant `balance == address(this).balance`, resulting in the contract becoming insolvent.

**This is not:** A complex multi-step attack requiring privileged access or external dependencies.  
**This is:** A single-transaction reentrancy that corrupts fundamental accounting state.

---

> An unprivileged attacker owning two staked services can call `unstake()` and re-enter during the ETH transfer callback to unstake a second service, causing the `balance` state variable to be decremented only once while ETH is transferred twice.

**Proof:** `PoC L#425-428`:

## Violated Core Invariant

> **"Contract balance state variable MUST equal actual ETH held by the contract"**  
> `balance == address(stakingContract).balance`

**Evidence:** PoC demonstrates post-attack state where:
- `balance` (storage) = 99,857 mETH
- `address(this).balance` (actual) = 99,714 mETH
- **Invariant broken by 142 mETH**

**PoC L#416-417:**

## Impact

The **staking contract and all future stakers** suffer permanent insolvency. The attacker gains the accounting discrepancy (142 mETH demonstrated), which represents rewards that should have been tracked but weren't.

| Impact Type | Description | Evidence |
|-------------|-------------|----------|
| **Direct Loss** | Contract believes it has more ETH than it actually holds | `balance > actualETH` post-attack |
| **Cascading Effect** | Future reward calculations based on inflated `balance` | `availableRewards` derives from `balance` |
| **Permanent** | No recovery mechanism; requires contract migration | State permanently corrupted |

## Root Cause

In [StakingBase.sol:929-947](https://github.com/valory-xyz/autonolas-registries/blob/be1057a5e37f17f26b13c41311fe0e8e40259484/contracts/staking/StakingBase.sol#L929-L948), the `_withdraw()` function updates the `balance` state variable **after** all ETH transfers complete, following a vulnerable pattern:

[contracts/staking/StakingNativeToken.sol](https://github.com/valory-xyz/autonolas-registries/blob/be1057a5e37f17f26b13c41311fe0e8e40259484/contracts/staking/StakingNativeToken.sol#L27-L33) (Lines 27-33):
