Fill-or-Kill Orders Incorrectly Revert on Lot-Size Dust

## Summary

The implementation of FOK orders rejects any order where post-lot-rounding a tiny “dust” remainder (>0) remains. Spec says “dust may remain and the order should still succeed so long as the filled amount ≥ requested minus dust,” but code instead does:


Thus all FOK orders that aren’t exact multiples of lot size now revert, breaking the FOK guarantee.

## Vulnerability Description
→ Caller posts a FOK buy for `baseAmount = 1.005 × lotSize`.

→ Internal rounding to `floor(amount / lotSize) * lotSize` leaves `0.005 × lotSize` dust.

→  Because `newOrder.amount > 0`, the code does `revert FOKOrderNotFilled()`.

→ According to spec, the order should fill the `1×lot`, ignore the dust, and return success (dust unfilled).

→ Both `_processFillBidOrder` and `_processFillAskOrder` contain the same guard.



## Impact
Users attempting legitimate FOK trades with sizes that are not lot-aligned will always revert, blocking an advertised order type. No value is stolen or locked — just broken functionality.
