Fill-or-Kill (FOK) Orders Incorrectly Revert Due to Unfillable Lot Size Remainder (Dust)

## Summary
The Fill-or-Kill (FOK) order functionality in `CLOB.sol` is flawed. It causes transactions to revert if any "dust" amount remains after matching, even when this dust is untradeable due to the market's `lotSizeInBase` constraint. This contradicts the expected behavior of a FOK order, which should only fail if the *tradeable* portion cannot be filled completely.

## Finding Description
A FOK order requires the entire order to be filled immediately and in its entirety, or the transaction must be reverted. The `CLOB.sol` contract implements markets with a `lotSizeInBase`, which is the smallest indivisible unit of the base asset that can be traded.

When a taker order is matched against resting limit orders, the fill amount is rounded down to the nearest lot size. This can result in a small, remaining portion of the taker's order that is smaller than one `lotSizeInBase` (i.e., "dust"). This dust amount is fundamentally untradeable.

This logic is too simplistic. It reverts if any amount of the order remains (newOrder.amount > 0), failing to distinguish between a failure due to insufficient liquidity and a success where only untradeable dust is left.

Scenario:
1. A market is configured with `lotSizeInBase = 1 ether`.
2. A resting limit order exists to sell `100 ETH`.
3. A user submits a FOK order via `postFillOrder` to buy `100.5 ether`.
4. The matching engine fills `100 ether`. The remaining `newOrder.amount` is `0.5 ether`.
5. The check `newOrder.amount > 0` evaluates to true, and the transaction incorrectly reverts with `FOKOrderNotFilled()`, failing the user's otherwise successful trade.

## Impact Explanation
This is a significant correctness bug that severely degrades a core feature of the protocol. The FOK order type becomes unreliable and unusable in practice, as users' valid trades will frequently and unexpectedly fail due to common rounding artifacts. This breaks the functional promise of the FOK order type and harms the user experience, potentially driving users away. While it doesn't cause a direct loss of funds, it prevents the intended functionality of the exchange.

## Likelihood Explanation
 In any active market, it is very common for a taker's desired trade size not to be an exact multiple of the available liquidity's lot sizes. Any user attempting a FOK order in such a common scenario will have their transaction reverted, making the occurrence of this bug highly likely in a live environment.
