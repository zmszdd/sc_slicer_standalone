sUSDM.decimals() returns 6 instead of ERC-4626 compliant 12, causing 10^6 overestimation for integrating protocols

### Summary

`sUSDM` is an ERC-4626 vault wrapping USDM (6 decimals). It overrides `_decimalsOffset()` to return 6, which causes OpenZeppelin's `ERC4626Upgradeable` to mint shares in 12-decimal precision (virtual shares = `10^6`). However, `sUSDM` also overrides `decimals()` to return a hardcoded `6` instead of the ERC-4626 standard value of `underlyingDecimals + _decimalsOffset() = 12`.

This creates a mismatch: **the internal share accounting operates at 12-decimal precision, but `decimals()` tells external consumers that shares are 6-decimal**. Any protocol integrating sUSDM (lending markets, DEX aggregators, oracles) that uses `decimals()` to interpret `balanceOf()` values will overestimate holdings by a factor of **10^6 (one million)**.

Note: `decimals()` is not merely a display hint. EIP-4626 inherits EIP-20's requirement that `decimals()` "MUST return the number of decimals the token uses" — i.e., the actual scaling factor needed to convert between raw amounts and human-readable units. OpenZeppelin's ERC-4626 implementation enforces this by computing `decimals() = underlyingDecimals + _decimalsOffset()`, tying the return value directly to the share conversion math. sUSDM's override severs this link.

Concrete impact scenarios:

1. **Lending protocols**: A user deposits 100 USDM into sUSDM, receiving ~100e12 raw shares. A lending protocol reads `balanceOf = 100e12` and `decimals() = 6`, computing `100e12 / 1e6 = 100,000,000` tokens as collateral value. The correct value is `100e12 / 1e12 = 100` tokens. The user can borrow **1,000,000x** more than they should.

2. **DEX pricing**: AMMs or aggregators pricing sUSDM will miscalculate token amounts by 10^6, leading to massively incorrect swap rates.

3. **Portfolio trackers / wallets**: Users see 1,000,000x inflated balances.

4. **Oracle feeds**: Any oracle composing sUSDM price from on-chain data using `decimals()` will produce prices off by 10^6.

sUSDM is explicitly designed for DeFi composability — the contract is described as a "wstETH-style appreciation model" ERC-4626 vault, intended to be held, transferred, and used as collateral across the ecosystem. Any integration that follows the ERC-20/ERC-4626 standard to interpret sUSDM balances will be affected.
