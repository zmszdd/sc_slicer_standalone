# 阶段二通用性评测口径

目标是让阶段二独立地从 `report.json` 推导报告声称的 P/I/V 和候选约束；不要求逐例人工审批，
也不把代码、PoC、修复后的真实行为当作本阶段的输入或正确性结论。

## 自动输出与边界

每次完整运行的 `auto-triage.json` 只负责路由：

- `candidate`：当前证据和程序检查允许输出**候选**约束，仍非语义真值或 PoC 一致性结论。
- `review`：公式已形成，但报告歧义、遗漏条件、覆盖不全等原因需独立复核。
- `abstain`：核心 P/I/V 无法完整形式化，不应强制生成完整公式。
  当内部查询 `P∧V` 不可满足或未知时，也必须暂缓该核心约束，不能把它当作有效反例。
- `pipeline_failure`：模型超时、空/非法响应或程序异常；这是工程失败，不能计作语义拒答。

`formalization-attempts.json` 保存第二步每次尝试及错误。首次尝试的原始输出仍在
`neural-formalization/`，可选重试在 `neural-formalization-retry-1/`。显式使用
`--formal-retries 1` 才会额外调用模型一次；默认 0 保持历史实验的调用上限。
只重试空/非法 JSON、超时、无效形式计划；模型报错或工具调用违规不会重试。

## 通用评测，不把五例草案硬当金标准

1. 先冻结模型/提示版本、输入白名单、重试次数和样本选择规则。按项目及漏洞类型分层抽取
   *未参与提示设计*的报告；保留原始输入与输出哈希。缺 PoC 或修复的报告也可纳入阶段二。
2. 对全部样本自动统计：第一步完成率、第二步可解析率、SMT/Z3 完成率、四种路由占比、
   每例调用次数和耗时。`pipeline_failure` 单列，不并入 `abstain`。
3. 从 `candidate`、`review`、`abstain` 各层随机抽样，再加错误类型定向抽样，由独立审核者
   仅核对报告语义：P 是否包含必要触发条件而无结果；I 是否准确限定范围与方向；
   V 是否为报告声称的直接违反。逐项标 `supported` / `contradicted` / `unknown`，
   记录证据 ID 和理由。`unknown` 不算正确或错误，也不能强行批准。
4. 分别报告自动覆盖率（`candidate / 全部`）、候选语义错误率（审核过的候选中错误数/可判定数）、
   各 P/I/V 维度错误率和 `unknown` 比率；给出每类样本数量。不用五例百分比外推总体。
5. `gold_v1/` 保留为历史草案/参考案例；未完成独立核验之前，不能把它或助手自评分数称为金标准。
   人工主要用于抽样评测及疑难分流，不是每份报告进入阶段二的前置审批。

本阶段的 Z3 检查只证明所生成公式的内部关系，不证明报告说法真实或 PoC 与报告一致。
