Insolvency and Denial of Service due to Fee-on-Transfer Token Support Mismatch

## Finding description and impact

The `DistributionCreator` contract accepts arbitrary ERC20 tokens for reward distribution. However, the system's internal accounting logic in `increaseTokenBalance` assumes that the balance increase in the contract exactly matches the input `amount` parameter. This assumption fails for **Fee-on-Transfer (FoT)** tokens or tokens with transfer inaccuracies (e.g., rounding loss in **stETH**).

The `increaseTokenBalance` function updates the user's internal ledger (`creatorBalance`) using the input `amount` parameter, ignoring the actual number of tokens received by the contract.


When a creator subsequently calls `createCampaign` (which invokes `_pullTokens`), the contract validates solvability against this inflated `creatorBalance`. It then attempts to transfer the full nominal amount to the distributor using the contract's pooled token balance.

Because the contract physically holds fewer tokens than the sum of all `creatorBalance` ledgers, any user depositing FoT tokens (or tokens with slight rounding loss like stETH) effectively creates a system-wide deficit.


### Impact

This discrepancy creates a system-wide **insolvency**.

1.  User A deposits 1,000 FoT tokens (1% fee). The contract receives 990, but credits User A with 1,000.
2.  User B deposits 1,000 standard tokens. The contract receives 1,000, credits User B with 1,000.
3.  **Total Physical Balance:** 1,990. **Total Liabilities:** 2,000.
4.  User A creates a campaign for 1,000. The transfer succeeds by using 10 tokens from User B's deposit.
5.  User B attempts to use their recorded balance of 1,000. The transaction reverts (`ERC20: transfer amount exceeds balance`) because the contract only has 990 remaining.

This results in a permanent DoS and fund loss for the last user attempting to withdraw or use their balance.
