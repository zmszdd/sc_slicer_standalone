# 阶段二提取前信息充分性筛选测试（2026-09-19）

## 目标

把案例筛选移动到 P/I/V 提取之前。DeepSeek 只依据 `report.json` 的编号标题、描述和影响，检查四项最低信息：受影响对象、触发条件或行为、直接效果、可推导安全关系的依据。任一项为 `missing` 或 `uncertain`，立即停止，不生成 `elements.json`。本测试未读取或发送 PoC、修复建议和合约代码。

## 结果

| 案例 | 入口判断 | 后续行为 | API 调用 |
| --- | --- | --- | ---: |
| Intuition `wC4QDwrRjko` | `insufficient`：安全关系依据不确定 | `excluded_before_extraction`；没有 `elements.json` | 1 |
| GTE CLOB `6BVtiNy49JH` | `ready`：四项均有编号证据 | 允许进入 P/I/V；模型生成了要素响应，随后原有要素校验因攻击步骤未引用 action 而拒绝 | 2 |

这验证了入口门的职责边界：信息不足的报告不会消耗后续 P/I/V 调用；信息充分只代表允许尝试提取，不保证模型输出通过原有结构与证据校验。第二例的后续拒绝不是入口筛选失败，而是规则化过程中的模型输出问题。

第一次 Intuition 试跑中，模型把 `safety_relation_basis` 标成 `uncertain`，但遗漏在冗余的 `missing_dimensions` 列表中，导致格式拒绝。程序现从四项已校验状态确定性重建该列表；语义判断本身未被程序改写。修正后的运行得到受控排除。

## 当前边界

- 这是两个开发案例，不是筛选准确率。
- 入口判定仍由 DeepSeek 完成，可能误排除或误放行；后续应冻结规则后抽取一批新报告，人工只审核四项充分性。
- 提取后的证据、类型、形式化和 Z3 校验继续保留，因为它们属于生成结果合法性检查；旧的额外后筛选和语义复核不再参与活动工作流。
