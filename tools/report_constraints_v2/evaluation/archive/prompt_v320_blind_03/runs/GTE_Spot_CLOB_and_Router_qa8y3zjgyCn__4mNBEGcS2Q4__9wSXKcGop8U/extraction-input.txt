Bitwise zero check causes incorrect `ZeroCostTrade() `reverts for valid partial fills

## Finding description

In both `_processLimitBidOrder` and `_processLimitAskOrder`, the code tries to detect zero-cost trades with a bitwise test instead of a logical zero check:


The intended condition is to revert if either side of the trade is 0.
But the implementation is wrong, as `a & b == 0` is not equivalent to `(a == 0 || b == 0)`. Many non-zero integer pairs satisfy a & b == 0 (See PoC for the values used). As a result, the code will trigger false positives and valid limit orders that partially fill will revert with `ZeroCostTrade()`.

## Impact

Any partial-fill of limit orders where the computed base and quote transfer amounts are both non-zero but where `a & b == 0` will revert.

This even introduces a griefing vector where an attacker could create an order to match a victim's one to trigger the `(a & b) == 0 ` condition on purpose and make their limit post fail.

Note that this affects both ask and bid limit paths.
