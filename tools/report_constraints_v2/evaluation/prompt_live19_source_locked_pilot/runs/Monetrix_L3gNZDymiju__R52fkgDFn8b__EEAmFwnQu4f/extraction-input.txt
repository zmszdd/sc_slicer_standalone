BLP supply can brick backing reads when HyperCore does not activate the supplied slot

# Finding Description and Impact
`MonetrixVault.supplyToBlp()` registers a BLP supplied slot after sending action 15 without proving HyperCore activated the 0x811 slot. If the action is accepted but the slot remains unreadable, Accountant backing/surplus reads and settlement revert until cleanup.

- No postcondition read is performed before `notifyVaultSupply`.
- `sendSupply()` only forwards the raw borrow/lend action.
- Every registered slot is later treated as an activated strict-read slot.

### **Exploit Path**
1. The Vault has an Accountant configured and no active registration for the target BLP slot.
2. The operator calls `supplyToBlp`; the EVM CoreWriter call succeeds, but HyperCore leaves the 0x811 supplied-balance slot inactive.
3. The Vault still calls `notifyVaultSupply`, adding that token to `vaultSupplied`.
4. Later `totalBackingSigned()`, `distributableSurplus()`, and `settleDailyPnL()` revert until `removeSuppliedEntry` clears it.

### **Impact**
- Yield settlement is blocked because Gate 3 needs a successful `distributableSurplus()` calculation.
- Vault backing/surplus accounting and monitoring are unavailable while the stale slot remains registered.

Because this causes the stated Medium impact, this warrants the selected severity.

### **Recommended Mitigation Steps**
- In `MonetrixVault.supplyToBlp()`, call `notifyVaultSupply` only after verifying the supplied slot is readable and active.
- If HyperCore activation can be asynchronous, use pending registration and promote it only after a successful `suppliedBalance` read.
- Keep `removeSuppliedEntry` as repair, but do not rely on it to prevent bad registrations.
