Incorrect exchange rate when there are queued withdrawals

## Finding description and impact

When there are queued withdrawals the `slashingAmount` and the `rewardsAmount` are not correctly distributed. This is because the `kHype` is not yet burned and the `totalClaimed` has not been decremented yet and the queued withdrawal's exchange rate is already locked in. Therefore, when there are rewards users will receive less than expected and when there are slashing events the amount will not be subtracted from the kHype holders correctly leaving the protocol at a loss.

For example:
NOTE: no withdrawal fees for simplicity
These are the same values used in the PoC for the rewards scenario.
1. user1 stakes 1e18 HYPE
2. user1 minted 1e18 kHype
3. Validator rewards 1e18 HYPE
4. Current exchange rate is `1e18 kHype :  2e18 HYPE`
5. user1 `queuesWithdrawal` for by locking 1e18 kHype for `2e18 HYPE`
6. user2 deposit `1e18 HYPE`
7. user2 minted `0.5e18` kHYPE
8. Validator rewards 1e18 HYPE
9. user2 `queuesWithdrawal` for `0.5e18 kHype` with exchange rate calculated as follows:

`NOTE: assume precision is maintained`

exchangeRate = totalHYPE / totalKHYPESupply

totalHYPE = totalStaked + rewardsAmount - totalClaimed - slashingAmount
totalHYPE = 2e18 + 2e18 - 0 - 0
totalHYPE = 4e18

totalKHYPESupply = 1e18 + 0.5e18
totalKHYPESupply = 1.5e18

exchangeRate = 4e18 / 1.5e18 = 2.6667e18

Thus, the queued withdrawal for user2 will be `(0.5e18 kHyp * 2.6667e18) = 1.333e18 Hype`

The total withdrawn amount is  `1.333e18 HYPE + 2e18 HYPE = 3.333e18 HYPE` and `user2 loses 0.666e18 HYPE and it is left in the contract`
