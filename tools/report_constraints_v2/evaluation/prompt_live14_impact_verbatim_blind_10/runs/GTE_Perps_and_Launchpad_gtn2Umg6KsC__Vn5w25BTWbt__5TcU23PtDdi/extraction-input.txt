Malicious users can permanently DoS the Reward Fee distribution system by front-running pair creation

## Finding description

Protocol : Launchpad

The `GTELaunchpadV2PairFactory` factory creates TWO types of pairs based on the caller:

Type A: Regular pairs without reward fee mechanism  
(launchpadLp == launchpadFeeDistributor == address(0)) 

Type B: Launchpad pairs with fee related variables set 
(launchpadLp != launchpadFeeDistributor != address(0) )


Rewards fee calculation / distribution are only activated when pairs are created thru the launchpad.


However, since the `launchToken` address becomes public, after it is deployed thru the`launch` function [here](https://github.com/code-423n4/2025-08-gte-perps/blob/main/contracts/launchpad/Launchpad.sol#L252)
An attacker can front-run and create a pair for `LaunchToken: quoteToken` pair, much before 
the launchpad's `createPair() ` call at the end of bonding phase. 
This permanently disables the fee reward mechanism for graduated tokens.

Also note that, only ONE pair can exist for any (tokenA, tokenB) combination.
The first caller (whether launchpad or attacker) creates the pair
subsequent calls for the same tokens will revert with "PAIR_EXISTS".


Although the revert is handled during graduation, 
The Launchpad is still forced to use the already created pair with permanently disabled reward system.


## Impacts and Likelihood

Impact : High

1. Attackers can permanently disable reward fee calculation / distribution mechanism of graduated pairs.
2. No rewards are distributed to users who purchased in bonding phase.
3. `endRewards` calls the wrong address bricking last user transfer.

Likelihood : High

1. All launchpad graduating pairs can be impacted, as anyone can easily execute the attack.
