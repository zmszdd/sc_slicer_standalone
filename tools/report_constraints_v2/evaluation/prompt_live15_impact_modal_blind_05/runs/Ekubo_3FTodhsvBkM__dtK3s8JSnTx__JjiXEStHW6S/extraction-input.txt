deposit ignores maxAmount0/maxAmount1 in the lock callback, allowing overspend if pool state changes in TWAMM pool

## Finding description and impact

`BasePositions.deposit` enforces `liquidity < minLiquidity` before the `lock` call via


However, in a TWAMM pool,  `sqrtRatio` can change in `TWAMM.lockAndExecuteVirtualOrders.`

Which is called by `BasePositions.handleLockData` → `CORE.updatePosition` → `beforeUpdatePosition` → `lockAndExecuteVirtualOrders`.

`lockAndExecuteVirtualOrders` executes pending virtual orders and updates `sqrtRatio`.

This causes the user to possibly spend more than `maxAmount0`/`maxAmount1` since the slippage limit is only checked before the pending virtual orders executions. 

And the deposit is processed after the pending virtual orders execute and update the `sqrtRatio`.
