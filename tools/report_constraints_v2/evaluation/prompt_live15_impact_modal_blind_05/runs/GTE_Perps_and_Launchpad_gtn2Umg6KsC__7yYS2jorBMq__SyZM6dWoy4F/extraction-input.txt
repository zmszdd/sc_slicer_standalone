Incorrect trigger condition in LaunchToken::_decreaseFeeShares() causes permanent DoS of GTELaunchpadV2Pair functions

## Summary

The `LaunchToken::_decreaseFeeShares()` function contains an incorrect trigger condition that prevents the rewards accrual mechanism from being properly terminated. This issue causes the `GTELaunchpadV2Pair`'s core functions (`mint()`, `burn()`, `swap()`, and `sync()`) to become permanently blocked, rendering the pair contract unusable and freezing all assets locked within it.

## Finding Impact

**Impact: High**

The impact is assessed as high because:

1. The issue causes a permanent denial of service for critical functions of the `GTELaunchpadV2Pair` contract:
   - `mint()` - Adding liquidity becomes impossible
   - `burn()` - Removing liquidity becomes impossible
   - `swap()` - Trading tokens becomes impossible
   - `sync()` - Synchronizing reserves becomes impossible

2. All launch/base tokens and quote tokens locked in the affected pairs become permanently frozen, resulting in a complete loss of funds for the token launchers (projects partnering with GTE) and other liquidity providers.

3. The issue affects all pairs created for all launch tokens, making it a systemic vulnerability across the entire protocol.

## Finding Likelihood

**Likelihood: High**

The likelihood is assessed as high because:

1. The issue is triggered by a common sequence of events in the protocol's normal operation:
   - Launch token is created and bonded
   - Token reaches bonding price and is graduated (unlocked = true)
   - Users transfer their tokens, decreasing totalFeeShare to zero

2. The incorrect condition is hardcoded in the core contract and will be executed for every launch token in the protocol.

3. Once the launch token is graduated (unlocked = true), there is no way to call `endRewardsAccrual()` to deactivate the rewards pool, which means the issue will inevitably occur when totalFeeShare reaches zero.

## Finding Description

The root cause of this issue is an incorrect trigger condition in the `LaunchToken::_decreaseFeeShares()` function:


The issue occurs because the condition `if (totalFeeShare == 0 && !unlocked)` is incorrect. During the bonding period (`unlocked = false`), the `totalFeeShare` tends to increase as users buy the launch token. Once the token hits the bonding price, it's graduated and the unbonding period starts (`unlocked = true`).

The correct condition should be `if (totalFeeShare == 0 && unlocked)` because:

1. During the bonding period (`unlocked = false`), the pair contract doesn't exist yet, so calling `_endRewards()` would revert.
2. The rewards program should only be ended after the token is graduated (`unlocked = true`) and no more pre-bonding shares exist (`totalFeeShare = 0`).

This incorrect condition causes the following sequence of events:

1. A launch token is created and users buy tokens during the bonding period, increasing `totalFeeShare`.
2. The token reaches its bonding price and is graduated (`unlocked = true`).
3. After graduation, users transfer all their tokens, causing `_decreaseFeeShares()` to be called multiple times.
4. Eventually, `totalFeeShare` reaches 0, but since `unlocked = true`, the condition `totalFeeShare == 0 && !unlocked` is never satisfied.
5. `_endRewards()` is never called, so `GTELaunchpadV2Pair::endRewardsAccrual()` is never executed.
6. The pair continues to accrue rewards even though there are no more shares to incentivize.
7. When a user tries to perform a swap, mint, burn, or sync operation, the transaction reverts because:
   - `_update()` is called
   - `_distributeLaunchpadFees()` is called if there are accrued fees
   - `Distributor::addRewards()` reverts with `NoSharesToIncentivize` since `rs.totalShares = 0`
