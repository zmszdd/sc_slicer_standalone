# Strict Fee Validation in Inherited `OAppSender` Breaks `feeBufferBPS` Functionality

## Description

The `UnstakeMessenger` contract introduces a `feeBufferBPS` state variable, intended to allow users (or frontends) to include a safety buffer in `msg.value` to protect against gas price fluctuations during cross-chain messaging.

However, the contract inherits from LayerZero's `OAppSender`. The `_lzSend` function in the standard `OAppSender` implementation (specifically the internal `_payNative` helper) strictly validates that `msg.value` equals the exact required native fee:


Since `UnstakeMessenger.sol` does not override this behavior, any user attempting to utilize the protocol's intended `feeBufferBPS` feature by sending `fee + buffer` will experience an immediate revert (`NotEnoughNative`).

This renders the `feeBufferBPS` mechanism useless and misleading. Users attempting to ensure transaction success by overpaying (as implied by the existence of a buffer configuration) will ironically face a Denial of Service.


## Risk

**Likelihood**:
High. The contract explicitly contains variables and logic for buffering fees. Frontends or integrations following this logic will inevitably send excess ETH, causing transaction failures.

**Impact**:
Medium. Broken core functionality. The "Safe/Buffered" transaction path is permanently broken. While funds are not lost (they revert), the protocol fails to deliver the promised reliability feature.
