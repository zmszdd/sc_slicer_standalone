StakingManager: Incorrect timing of usage of exchange rate on withdrawal

## Finding Description and Impact

Summary

When users withdraw kHYPE tokens, the protocol uses the exchange rate from when the withdrawal was queued rather than when it is confirmed to determine how much HYPE token they receive. This allows users to time their withdrawals and profit when the exchange rate decreases between queuing and confirmation, effectively extracting value from the protocol.

When a user queues a withdrawal of kHYPE tokens via the queueWithdrawal function, they provide the kHYPE amount they want to withdraw. The exchange rate is then used to determine how much HYPE token they can withdraw.

Once the minimumum withdrawal period ends(7 days minimum) the user can withdraw the equivalent amount of HYPE tokens at any time by calling the confirmWithdrawal function, which in turn calls the _processConfirmation function.

However this amount is based off an outdated exchange rate set during queue because If the exchange rate changes during period between queue and confirmation, it will render the exchange rate calculation in queue irrelevant.

As we can see above the protocol uses the hype amount calculated during queue, which is at least 7 days old, allowing users to profit if the exchange rate decreases during this period.

Consider the following:

1. User A deposits 100 HYPE and receives 100 kHYPE tokens
2. The exchange rate improves (e.g., due to rewards): 100 kHYPE = 110 HYPE
3. User A queues a withdrawal of their 100 kHYPE
4. System calculates they'll receive 110 HYPE (minus fees)
5. During the withdrawal delay period, the exchange rate drops due to slashing events. New rate: 100 kHYPE = 90 HYPE.
6. User A confirms the withdrawal after withdraw delay period.
7. They receive the originally calculated 110 HYPE.
8. But their kHYPE was only worth 90 HYPE at confirmation time.
9. They have profited 20 HYPE from the protocol.

This vulnerability essentially gives users an incentive to time when they withdraw, to extract excess value from the protocol during downturns, creating a "bank run" risk and potentially leading to protocol insolvency.
