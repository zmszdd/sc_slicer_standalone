Incorrect Pair Address Calculation in `endRewards` Function

## Finding description and impact

The `endRewards` function in `Launchpad.sol` calculates the Uniswap V2 pair address using the `pairFor` function, which computes the address based on `token0`, `token1`, and `uniV2InitCodeHash`:


However, the `createPair` function in `GTELaunchpadV2PairFactory.sol` uses a different `salt` that includes `_launchpadLp` and `_launchpadFeeDistributor`:


This discrepancy in the `salt` calculation causes the pair address computed by `pairFor` to always differ from the actual pair address created by `createPair` during the `_createPairAndSwapRemaining` function in `Launchpad.sol` when a token launch graduates. As a result, the `endRewards` function, which calls `distributor.endRewards(pair)`:


always reverts due to an invalid pair address, preventing the protocol from terminating the rewards accrual process for a launched token.

**Impact**:  
This vulnerability causes a Denial of Service (DoS) for the `endRewards` function, a critical protocol feature intended to stop rewards accrual (e.g., when `totalFeeShare` reaches zero in `LaunchToken.sol`). The issue affects all token launches, as the incorrect pair address calculation is inherent to the `pairFor` function. This disrupts the protocol's ability to manage rewards, undermining its core functionality and reliability. According to Code4rena guidelines, this qualifies as a **High** severity issue due to its direct impact on a critical protocol function without requiring user error or specific conditions.
