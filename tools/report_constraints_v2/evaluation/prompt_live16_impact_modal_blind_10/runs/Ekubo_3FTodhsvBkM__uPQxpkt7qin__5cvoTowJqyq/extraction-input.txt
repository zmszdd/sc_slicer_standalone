Mev capture swaps have one superior path between exactIn/exactOut swaps leading to overpay/underpay in fees

## Finding description and impact 

`MevCapture` extension records tick in the pool at the beginning of the block and after every swap takes additional fee proportional to the distance between tick after the swap and tick at the beginning of the block.
Users can swap  using exactOut swaps or exactIn swaps.
In mev capture when user is swapping using exactIn swap, the additional Mev capture fee is taken on the output amount.
When user is swapping using exactOutput swap, the additional Mev capture fee is added to the input amount.

This leads to situation where most of the time one of the paths (ExactIn swap, ExactOut swap) overpays/underpays in comparison to the other.

As lets imagine that at the beginning of the block, pool is at tick X.

**ExactIn scenario** :  User wants to swap using exactIn providing `amountIn` amount of tokens. In the pool the actual priceImpactAmount is `amountIn` - fee. Price Impact amount moves the price by some Z amount of ticks. The `amount out` is calculated and returned to the Mev capture. Mev capture based on the distance between tick in the pool and tick at the beginning of the block ( |X + Z - X | * fee) takes additional fee from `amount out`. So `amountOut` = `amountOut` - additionalFee

**ExactOut scenario**:
Now what if instead of exactIn swap, user would perform an exactOut swap with exact output amount = `amountOut` - additionalFee ? :
Mev capture will first swap using Core. Then inside the core :
Because the `amountOut-additionalFee` is smaller than the amountOut from the previous scenario, the amountIn required to get this exact out amount of tokens is also smaller.  This means that actual price impact will be smaller, this leads to situation where price is moved by G ticks and G < Z.
After the swap in the core, Mev capture based on the distance between tick in the pool and the tick at the beginning at the block (|X+ G - X| * fee) adds additional fee to `amountIn`. So `amountIn` += additionalFee

So exact output swap in this scenario will move price by less ticks, so while receiving the same amount of output tokens it will pay less amount of token in.

I added POC that illustrates the scenario outlined above showing that in this scenario exact Out is superior.

This finding shows that certain users will overpay/underpay compared to others, leading to the loss/gain for some of them and unexpected results.
