Blacklisted users can bypass restrictions and unstake funds via `unstakeThroughComposer` if already in cooldown

## Finding description and impact

**Root Cause:**
The protocol implements a `FULL_RESTRICTED_STAKER_ROLE` (blacklist) intended to freeze the assets and activities of malicious users. This restriction is enforced in `_withdraw` and `_beforeTokenTransfer` within the base `StakediTry` contract.

However, the `unstakeThroughComposer` function in `StakediTryCrosschain` bypasses these standard withdrawal checks.
1.  When a user enters the cooldown period, their assets are moved from the `StakediTry` vault to the `iTrySilo`.
2.  The `unstakeThroughComposer` function interacts directly with the silo and the `cooldowns` mapping to withdraw funds.
3.  Crucially, this function **does not verify** if the `receiver` (the original user) has the `FULL_RESTRICTED_STAKER_ROLE`.

**Impact:**
A user who has been blacklisted (e.g., for malicious activity) AFTER entering the cooldown period can still successfully withdraw their funds. By triggering a cross-chain unstake request (or if the Composer processes a pending request), the funds will be withdrawn from the silo and bridged back to the user.

This completely negates the effectiveness of the blacklist for any funds that are already in the cooldown state. Since the cooldown period is typically when an admin would identify and blacklist a malicious actor, this loophole renders the "freeze" capability ineffective during the most critical window.

**Note:** The same vulnerability likely exists in the direct `unstake` function in `StakediTryV2` (StakediTryCooldown), as it also lacks a blacklist check on the receiver.
