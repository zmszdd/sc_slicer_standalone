RiskEngine.twapEMA() computes the wrong TWAP tick due to incorrect tuple unpacking of OraclePack.getEMAs()

## Finding description
`OraclePack.getEMAs()` has a well-defined return order:

So the tuple returned by getEMAs() is:

`spotEMA` (index 0)
`fastEMA` (index 1)
`slowEMA` (index 2)
`eonsEMA` (index 3)
`medianTick` (index 4)
However, `RiskEngine.twapEMA()` unpacks this tuple in the wrong order:

Solidity tuple assignment is positional, therefore this code assigns:

`eonsEMA <- spotEMA`
`slowEMA <- fastEMA`
`fastEMA <- slowEMA`
So the function does not compute the intended `0.6*fast + 0.3*slow + 0.1*eons`.It instead computes `(6 * slow + 3 * fast + spot) / 10`
This is further confirmed by `RiskEngine.isSafeMode()`, which unpacks `getEMAs()` using the correct order:
Meaning `twapEMA()` is internally inconsistent with the rest of the system’s own interpretation of `getEMAs()`.

## Impact
This incorrect TWAP tick is consumed by the protocol via `PanopticPool.getTWAP()`:

`twapTick` is then used in `dispatchFrom()` (liquidations/force exercises/settlements):

- Manipulation / staleness guard uses `twapTick`:
- Solvency is explicitly checked at `twapTick`:
- Liquidation pricing and bonus use `twapTick`:
As a result, the system’s liquidation/dispatch logic relies on a TWAP that is mathematically different than intended. This can cause false positives/negatives in `StaleOracle()` checks, potentially allowing operations when the intended TWAP would block them, or blocking operations when the intended TWAP would allow them.

It can also cause incorrect solvency classification at the TWAP checkpoint (since one of the four price points in the solvency grid is wrong) ans also incorrect liquidation bonus / conversion pricing inputs (since `getLiquidationBonus` is fed `sqrtRatioAtTick(twapTick)`).
