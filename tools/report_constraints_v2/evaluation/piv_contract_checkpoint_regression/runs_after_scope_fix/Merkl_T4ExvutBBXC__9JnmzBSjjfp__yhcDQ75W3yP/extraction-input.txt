Fee-On-Transfer Tokens Cause Permanent Balance Inflation

## Summary

The `increaseTokenBalance()` function in `DistributionCreator.sol` credits users with the full `amount` parameter without verifying the actual tokens received. For fee-on-transfer (FoT) tokens, this creates a permanent accounting mismatch where recorded balances exceed actual contract holdings, leading to protocol insolvency.

## Vulnerability Detail

The `increaseTokenBalance()` function transfers tokens from the caller and credits the user's balance:


The issue is that `_updateBalance` credits the full `amount` without measuring how many tokens were actually received. For FoT tokens that deduct a percentage on each transfer, the contract receives fewer tokens than `amount` but credits the full value.

Example with 1% FoT token:
- User deposits 10,000 tokens
- Contract receives 9,900 tokens (after 1% fee)
- User's `creatorBalance` is credited 10,000 tokens
- 100 token deficit per deposit

As more users deposit, the deficit accumulates. When users attempt to withdraw via `decreaseTokenBalance()`, the last users will be unable to withdraw their full recorded balance because the contract lacks sufficient tokens.

## Impact

1. Balance Inflation: Recorded balances permanently exceed actual holdings, creating phantom balances.

2. Protocol Insolvency: The contract becomes insolvent - it owes more than it holds.

3. Last Depositor Loss: Users who withdraw later cannot receive their full balance. The deficit is socialized to the last withdrawers.

4. Campaign Funding Failures: Campaigns created using inflated balances will fail or underfund the Distributor contract.

Quantified Impact:
- With a 1% FoT token and 1,000,000 tokens deposited across users, the protocol has a 10,000 token deficit
- The last ~1% of withdrawers will be unable to withdraw anything
- With higher fee tokens (some FoT tokens have 5-10% fees), the impact scales proportionally
