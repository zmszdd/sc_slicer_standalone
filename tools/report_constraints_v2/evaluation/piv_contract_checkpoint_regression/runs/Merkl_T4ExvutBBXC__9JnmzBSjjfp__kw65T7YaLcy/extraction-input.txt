Fee-On-Transfer Dispute Token Permanently Bricks Protocol

## Summary

If a fee-on-transfer (FoT) token is configured as the `disputeToken`, the `resolveDispute()` function will permanently revert, leaving the protocol in an unrecoverable bricked state. This occurs because `disputeTree()` records the full `disputeAmount` but the contract receives fewer tokens due to the transfer fee, making it impossible to transfer back the recorded amount during resolution.

## Vulnerability Details

### Root Cause

Step 1 - Dispute Creation (`disputeTree`):


When a user calls `disputeTree()` with a FoT token:
- User sends `disputeAmount` tokens (e.g., 1000 tokens)
- FoT token deducts transfer fee (e.g., 1% = 10 tokens)
- Contract receives only 990 tokens
- Contract records `disputer = msg.sender` (no record of actual received amount)

Step 2 - Dispute Resolution (`resolveDispute`) - ALWAYS REVERTS:


Both branches attempt to transfer `disputeAmount` (1000 tokens), but:
- Contract only holds 990 tokens
- For FoT tokens, the transfer also burns a fee first, further reducing available balance
- Transfer reverts with "ERC20: transfer amount exceeds balance"

### State After Failed Resolution

Since `resolveDispute()` always reverts:
1. `disputer` remains set to the original disputer address (non-zero)
2. The dispute cannot be cleared through any mechanism
3. Protocol enters permanent freeze state

## Impact

### Permanent Protocol Freeze

1. Dispute Cannot Be Resolved:
- `resolveDispute(true)` reverts - cannot return stake to valid disputer
- `resolveDispute(false)` reverts - cannot slash stake to governor

2. `disputer` Remains Non-Zero Forever:
- `resolveDispute()` is the only function that sets `disputer = address(0)`
- Since it always reverts, `disputer` is permanently set

3. All Tree Updates Blocked:
No new Merkle trees can ever be published.

4. Tree Revocation Blocked:

5. Claims Frozen on Stale Data:
- Users can only claim from the old `lastTree`
- Any new rewards computed off-chain cannot be distributed
- Protocol becomes permanently non-functional

6. No Recovery Path:
- `recoverERC20()` cannot help because `resolveDispute()` needs to succeed first to clear `disputer`
- Even depositing more tokens doesn't help - the FoT token will take fees on the outgoing transfer too
- Contract upgrade/migration is the only recovery option

### Attack Vector

This is not a malicious attack - it occurs through legitimate protocol use:

1. Governor sets `disputeToken` to a FoT token (PAXG, some USDT implementations, deflationary tokens)
2. Honest user notices an incorrect Merkle tree
3. User calls `disputeTree()` - deposits tokens in good faith
4. Contract receives fewer tokens than recorded due to transfer fee
5. Governor attempts to resolve dispute (valid or invalid)
6. Transaction reverts - protocol is permanently bricked
