executeHedge Optimistically Registers Unsupported BLP Tokens, Bricking Protocol Accounting

## Finding description and impact

When [`executeHedge()`](https://github.com/code-423n4/2026-04-monetrix/blob/main/src/core/MonetrixVault.sol#L256-L276) is called with PM active, it buys the spot asset on L1 and immediately registers it in the accountant's [`vaultSupplied`](https://github.com/code-423n4/2026-04-monetrix/blob/main/src/core/MonetrixAccountant.sol#L70) registry via `notifyVaultSupply`:


The registration is unconditional. There is no check that BLP actually has an active reserve for this token. Under PM, HyperLiquid auto-supplies spot assets to BLP only if a BLP reserve exists for that token. If no reserve exists, the auto-supply silently does nothing on L1, but the EVM state still records the token as supplied.

[`_readL1Backing()`](https://github.com/code-423n4/2026-04-monetrix/blob/main/src/core/MonetrixAccountant.sol#L138-L172) later iterates `vaultSupplied` and calls [`suppliedBalance()`](https://github.com/code-423n4/2026-04-monetrix/blob/main/src/core/PrecompileReader.sol#L85-L91) for each entry, which queries the 0x811 precompile. The function enforces a hard requirement on the response:


On HyperEVM, querying 0x811 for a token that was never actually supplied to BLP produces a failure response. This causes `suppliedBalance` to revert. The revert propagates through the entire call stack:

- [`totalBackingSigned()`](https://github.com/code-423n4/2026-04-monetrix/blob/main/src/core/MonetrixAccountant.sol#L117-L135) calls `_readL1Backing`, reverts.
- [`surplus()`](https://github.com/code-423n4/2026-04-monetrix/blob/main/src/core/MonetrixAccountant.sol#L180-L182) calls `totalBackingSigned`, reverts.
- [`distributableSurplus()`](https://github.com/code-423n4/2026-04-monetrix/blob/main/src/core/MonetrixAccountant.sol#L187-L192) calls `surplus`, reverts.
- [`settleDailyPnL`](https://github.com/code-423n4/2026-04-monetrix/blob/main/src/core/MonetrixAccountant.sol#L213-L214) gate 3 calls `distributableSurplus`, reverts.

Every accounting read and yield settlement call is permanently bricked. The only recovery path is for an operator to call `removeSuppliedEntry` to remove the bad registry entry.
