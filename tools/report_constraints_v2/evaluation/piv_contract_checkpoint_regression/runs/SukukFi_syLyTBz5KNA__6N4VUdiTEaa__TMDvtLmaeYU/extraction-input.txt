Validator Batch Transfers Bypass KYC Enforcement

## Finding Description and Impact

`WERC7575ShareToken` enforces KYC on the standard user flows (`transfer`, `transferFrom`, `mint`, `burn`) by reverting when the recipient (and for mint/burn the holder) is not marked `isKycVerified`. The validator-only settlement helpers `batchTransfers` and `rBatchTransfers` bypass this gate: they directly mutate `_balances` (and `_rBalances` for rBatch) for arbitrary debtor/creditor pairs without checking `isKycVerified` and without `whenNotPaused`. 

A validator can therefore move funds from KYC-verified addresses to any non-KYC (or sanctioned) address in one call, defeating the on-chain compliance guarantee. Once received, those non-KYC addresses can route funds onward to KYC accounts using normal transfers (which only check the recipient), making this a practical, single key compliance bypass rather than a theoretical edge case. Pausing is also ineffective against the validator batch paths because they omit `whenNotPaused`.

This vulnerability is a KYC enforcement and access control logic flaw in the `WERC7575ShareToken` contract’s validator-only batch transfer mechanisms. The token enforces KYC checks via the isKycVerified mapping in its standard `transfer`, `transferFrom`, `mint`, and `burn` functions, but the `batchTransfers` and `rBatchTransfers` functions, which are restricted to the validator role, directly mutate `_balances` and `_rBalances` without consulting isKycVerified. As a result, these privileged batch operations bypass the on-chain KYC gating applied to normal user flows.

- This standard transfer function enforces the KYC policy: it requires `whenNotPaused` and explicitly reverts if the recipient `to` is not marked `isKycVerified`. This establishes the intended invariant that all token transfers must be KYC-gated, which the validator batch functions later violate.




- The `batchTransfers` validator-only function directly debits and credits `_balances` for multiple accounts without any `isKycVerified` checks and without `whenNotPaused`. A compromised/malicious validator can use this to move balances between arbitrary addresses, including non‑KYCed ones, bypassing the KYC restrictions applied in `transfer`/`transferFrom`.


- The `rBatchTransfers` validator-only function similarly consolidates transfers and iterates over aggregated accounts to update balances, again with no KYC verification on recipients or participants. This snippet shows the function entry and loop that processes accounts, illustrating that privileged batch settlement logic can mutate balances (and later `_rBalances`) without enforcing the on-chain KYC gating used in normal flows.

## Impact

- **KYC bypass by a single key**: Validator can route funds to unverified/sanctioned destinations in one call, nullifying the compliance invariant.
- **Pause bypass**: `batchTransfers`/`rBatchTransfers` ignore `whenNotPaused`, allowing fund movement even while the token is paused.
- **Regulatory/operational risk**: On-chain KYC guarantees become unreliable; downstream integrators relying on transfer gating are exposed.
