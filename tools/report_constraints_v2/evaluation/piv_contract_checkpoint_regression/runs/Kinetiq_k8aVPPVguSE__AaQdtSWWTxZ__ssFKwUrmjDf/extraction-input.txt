`StakingManager.sol` - Precision Loss in `redelegateWithdrawnHYPE` Leads to Permanent Value Lock in StakingManager

## Finding description and impact
**Description:**  
When a user cancels a withdrawal request (via the `cancelWithdrawal` function), the associated HYPE value (i.e., `totalHypeValueReturned`) is recorded in `_cancelledWithdrawalAmount`. Subsequently, an account with `MANAGER_ROLE` privileges can call the `redelegateWithdrawnHYPE` function, which reads the value of `_cancelledWithdrawalAmount`, resets it to zero, and re-delegates this HYPE amount through the `_distributeStake` function with the operation type `OperationType.SpotDeposit`.

In the `_distributeStake` function, when handling `SpotDeposit` or `RebalanceDeposit` types, the function calls `_convertTo8Decimals(amount, false)` to convert the 18-decimal `amount` into an 8-decimal `truncatedAmount`. The conversion logic is `truncatedAmount = amount / 1e10`, with the `roundUp` parameter set to `false`, meaning it always rounds down. However, unlike the handling of `UserDeposit` (see L464), the conversion process for `SpotDeposit` and `RebalanceDeposit` does not properly account for the remainder from `amount % 1e10`, i.e., the portion lost due to precision truncation. This remainder (less than `1e10` wei HYPE, equivalent to less than `1e-8` HYPE) is neither added back to `hypeBuffer` nor included in the `truncatedAmount` sent to L1.

**Impact:**  
Each time `redelegateWithdrawnHYPE` is used to re-delegate canceled withdrawal amounts, the rounding down in `_convertTo8Decimals`—without handling the remainder—causes `_cancelledWithdrawalAmount % 1e10` HYPE to be lost from the re-delegation process. This HYPE does not actually disappear from the system; it remains within the `StakingManager` contract (possibly in the contract’s ETH balance or an L1 account, depending on the fund flow implementation). However, it falls outside the protocol’s normal accounting and management mechanisms: it is neither recorded in `totalStaked`, explicitly tracked in `hypeBuffer`, nor delegated to validators to generate rewards.

As cancel-and-redelegate operations accumulate, this “lost” HYPE grows, becoming permanently stranded in the `StakingManager` contract, unusable by the protocol or returnable to users. This reduces the protocol’s capital efficiency and directly diminishes the potential profits for all kHYPE holders, effectively locking value permanently. Given that this issue could render protocol funds unproductive, it poses a high risk.
