AtomWallet 77-byte signatures do not authenticate `validUntil`/`validAfter`, allowing relayers to rewrite the execution window

## Finding description and impact

`AtomWallet` supports a 77-byte signature format: `r || s || v || validUntil || validAfter`.

The root cause is that the wallet does not authenticate the last 12 bytes.

In [`AtomWallet._validateSignature`](https://github.com/code-423n4/2026-03-intuition/blob/main/src/protocol/wallet/AtomWallet.sol#L294-L310), the contract first calls `_extractValidUntilAndValidAfterFromSignature(userOp.signature)`, which strips off the final 12 bytes and returns only the first 65 bytes as `rawSignature`.

Then the wallet verifies the owner signature only against:
- `userOpHash`
- the stripped 65-byte `rawSignature`

The parsed `validUntil` and `validAfter` values are only packed into `validationData` after recovery succeeds.

In [`AtomWallet._extractValidUntilAndValidAfterFromSignature`](https://github.com/code-423n4/2026-03-intuition/blob/main/src/protocol/wallet/AtomWallet.sol#L337-L360), the last 12 bytes are treated as metadata and are never included in the signed message.

This becomes exploitable because [`IEntryPoint.getUserOpHash`](https://github.com/code-423n4/2026-03-intuition/blob/main/lib/account-abstraction/contracts/interfaces/IEntryPoint.sol#L171-L178) explicitly hashes the UserOperation excluding the `signature` field. So changing the last 12 bytes of `userOp.signature` does not change `userOpHash`.

The project’s own helper also reflects this design: [`_signUserOpHashWithTimeWindow`](https://github.com/code-423n4/2026-03-intuition/blob/main/tests/unit/AtomWallet/AtomWallet.t.sol#L1010-L1020) signs `userOpHash` first and only then appends `validUntil` and `validAfter`.

As a result, any relayer/bundler that has a valid 77-byte signed operation can arbitrarily rewrite the time-window suffix without invalidating the owner’s signature.

This lets an attacker:
- change a future-only operation into one valid immediately
- remove expiry entirely by changing the suffix to `(0, 0)`
- extend or shorten the authorization window at will

Impact:
- the signer’s intended time restriction is not enforced
- stale signed `AtomWallet` operations can be executed outside the user-approved window
- since `AtomWallet.execute` can perform arbitrary calls, this can enable unauthorized token transfers, approvals, or other wallet actions at attacker-chosen times
