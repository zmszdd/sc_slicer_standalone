TrustBonding always penalizes active users to minimum reward floor due to incorrect utilization delta calculation

## Finding description and impact

`TrustBonding._getPersonalUtilizationRatio()` calculates the user's reward 
multiplier by computing a delta between two consecutive epoch utilization values:

The issue is that `getUserUtilizationInEpoch` uses `<=` instead of `<` when 
searching the user's epoch history, causing it to return the same stored value 
for both `epoch - 1` and `epoch` whenever the user's last active epoch equals 
`epoch - 1`. This means `rawUtilizationDelta` is always 0 for any user who was 
active in the previous epoch and inactive in the current one — which is the 
normal, expected behavior for a user interacting every epoch.

**The result:** every engaged user is permanently penalized to the 25% floor 
(`personalUtilizationLowerBound`) instead of receiving 100% of their eligible 
rewards. The only way to avoid the penalty under the current code is to skip 
at least two consecutive epochs before claiming — the exact opposite of the 
intended incentive design.

Impact:
- Permanent loss of 75% of rewards for every active user
- No attacker required — normal protocol usage triggers the bug
- Scales with emission volume and number of participants
- Disincentivizes exactly the behavior the protocol is designed to reward

The defensive fix can be applied directly inside `TrustBonding._getPersonalUtilizationRatio` 
(in-scope) without touching MultiVault. When both calls return the same value 
and the user had recorded activity in `epoch - 1`, the delta should be treated 
as the full utilization rather than zero:

The root cause is a `<=` vs `<` comparison in `MultiVault.getUserUtilizationInEpoch`, 
but since that file is outside the audit scope, the above guard in TrustBonding 
provides a robust in-scope mitigation that correctly handles the case.
