Missing rHYBR Validation in createGauge() Causes Permanent Fund Loss

## Finding description and impact

**Root Cause**
The vulnerability stems from missing input validation in the GaugeFactoryCL.createGauge() function combined with immutable architecture in the GaugeCL contract.

The ```rHYBR``` state variable defaults to ```address(0)``` upon contract deployment. The ```createGauge()``` function directly passes this value to the ```GaugeCL constructor``` without validating it's been initialized.

Immutable Gauge Architecture
Once a GaugeCL is deployed, its rHYBR address is immutable (set in constructor, no setter function). This design decision, while gas-efficient, creates a permanence problem when combined with the missing validation.

Deployment Sequence Dependency

The protocol assumes ```setRHYBR()``` will be called before any gauge creation, but enforces no such requirement. This creates a critical race condition during deployment.

## The vulnerability is silent until withdrawal, making it particularly dangerous.

**IMPACT**
1. Complete and Permanent Fund Loss 
When rHYBR == address(0) and rewards exist:

withdraw() always calls _getReward()
_getReward() attempts to call functions on address(0)
EVM reverts on all calls to address(0) (proven in test)
Withdrawal transaction fails completely
NFT remains locked forever

2.  No Recovery Mechanism
Only updates factory storage, doesn't affect already-deployed gauges. 
The Emergency Mode Insufficient
3. Protocol Reputation Damage 
   Immediate Loss of Trust: Users lose life savings in "unrecoverable" contract
   Legal Liability: Potential lawsuits for negligence
   Competitor Advantage: Other protocols capitalize on the failure
   Media Coverage: Negative press coverage in crypto media

4. Systemic DeFi Risk 
   If the broken gauge is whitelisted in other protocols:
   a. Composability breaks (gauge tokens become worthless)
   b. Downstream protocols may integrate broken gauges
