Accountant counts HyperCore 0x811 supply as backing without subtracting borrow debt

`PrecompileReader.suppliedBalance()` reads HyperCore precompile `0x811` and treats it as if it were a supplied-balance-only source:


That keeps only the fourth decoded word. The 0x811 user state is a borrow/lend user token state, not a pure supply balance. Its layout is:


So Monetrix books the asset side, `supply.value`, but drops the liability side, `borrow.value`.

`MonetrixAccountant.totalBackingSigned()` calls `_readL1Backing()` for the Vault and multisig L1 accounts. For each registered supplied slot, `_readL1Backing()` adds either `PrecompileReader.suppliedUsdcEvm(account)` or `PrecompileReader.suppliedNotionalUsdcFromPerp(...)` to backing. There is no matching read of `borrow.value`, no netting, and no check that the account has zero 0x811 borrow liability.

The inflated value feeds directly into the settlement gate:


Gate 3 in `settleDailyPnL()` requires `proposedYield <= distributableSurplus()`. That gate is supposed to keep Operator-submitted yield within real surplus. Here the bound itself is wrong because it is computed from gross 0x811 supply while ignoring 0x811 borrow debt.

This is not an Operator-compromise or arbitrary-destination issue. The Operator only calls the normal, code-bounded `settle()` and `distributeYield()` pipeline. The submitted yield is accepted by the protocol's own on-chain `distributableSurplus()` and APR cap. The bug is that the Accountant's on-chain safety bound overstates backing.

This is also in the audit's stated area of concern. The README explicitly calls out the Accountant 4-gate settle pipeline, vectors that over-report `totalBackingSigned()`, and HyperCore precompile read semantics. The affected files are in scope: `src/core/PrecompileReader.sol`, `src/core/MonetrixAccountant.sol`, and `src/core/MonetrixVault.sol`.

### Impact

When an L1 account has a counted 0x811 supply position and a 0x811 borrow liability, Monetrix can overstate USDM backing by the ignored borrow amount.

If the real net backing has no surplus, but `totalBackingSigned()` reports surplus because it counted gross supply, `settle()` can move principal USDC from the Vault to `YieldEscrow` as if it were yield. `distributeYield()` then finalizes the damage:

- the user share is minted as USDM and injected into sUSDM;
- the insurance share is deposited into `InsuranceFund`;
- the foundation share is transferred out as USDC.

The PoC demonstrates a 10,000 USDC unsupported yield distribution. After distribution, sUSDM assets increased, while USDM is underbacked by the same 10,000 USDC amount.

Medium severity is appropriate. The impact is real solvency damage, not rounding dust and not a display-only error. It is still bounded by normal settlement conditions, EVM USDC liquidity, the APR cap, and the need for a PM/BLP borrow liability to exist, so this is not a High-severity immediate drain.

### Why the same-token PoC is used

The PoC uses the same-token borrow/supply state as the minimal direct reproduction because it is exactly the four-word tuple decoded by `suppliedBalance()`. This directly shows that the contract reads `supply.value` while dropping the decoded `borrow.value`.

The root issue is broader than the same-token case: the settlement accounting has no path that subtracts 0x811 borrow liabilities for the account before treating 0x811 supply as USDM backing. In a cross-token PM state, the Accountant would also need to query and value borrowed-token liabilities, not only registered supplied-token assets.
