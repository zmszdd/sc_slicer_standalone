Same-block donation can indefinitely DoS Tokenomics.checkpoint()

### Summary
Every successful service donation updates `lastDonationBlockNumber = block.number`.
`Tokenomics.checkpoint()` unconditionally reverts if called in the same block as the most recent donation.
An attacker can watch the mempool for `checkpoint()` attempts and submit a donation in the same block (front-run/race), causing checkpoint to revert every time. This can delay epoch finalization indefinitely.

## Impact
- Epoch settlement liveness failure: `checkpoint()` can be delayed arbitrarily long.
- Cascading delays:
  - reward/top-up accounting finalization,
  - staking incentive pot updates,
  - any automation depending on timely epoch progression.
## Attack scenario
1) Keeper submits `checkpoint()` when epoch window is open.
2) Attacker submits a donation tx with higher priority.
3) Donation mined first → sets `lastDonationBlockNumber`.
4) `checkpoint()` mined in same block → reverts `SameBlockNumberViolation()`.
5) Attacker repeats indefinitely.
