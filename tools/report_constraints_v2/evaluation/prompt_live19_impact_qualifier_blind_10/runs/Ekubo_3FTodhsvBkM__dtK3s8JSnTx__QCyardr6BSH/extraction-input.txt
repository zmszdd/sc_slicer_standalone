`Positions.deposit` ignores user-supplied slippage limits (`maxAmount0`, `maxAmount1`), allowing unlimited financial loss in extension-enabled pools

## Finding description and impact

### Root Cause
The `deposit` function in `BasePositions.sol` allows users to specify `maxAmount0` and `maxAmount1` to limit the tokens they are willing to spend. However, the contract fails to enforce these limits during the settlement phase.

The logic flow creates a discrepancy between the **calculation** phase and the **execution** phase:

1.  **Calculation (Pre-Lock):** The function reads the *current* pool state (`sqrtRatio`) and calculates the exact amount of liquidity (`L`) that can be minted without exceeding `maxAmount0` or `maxAmount1` at that specific price.
2.  **Execution (Inside Lock):** The contract calls `CORE.updatePosition(..., L)`.
3.  **The Hook:** Inside `Core.sol`, the `beforeUpdatePosition` extension hook is triggered. For TWAMM pools, this executes pending virtual orders, which **moves the pool price (`sqrtRatio`) and tick**.
4.  **The Debt:** After the hook returns, `Core` calculates the token debt required to mint the fixed liquidity `L` at the **new, modified price**.
5.  **The Violation:** `Core` returns the new debt amounts to `BasePositions`. `BasePositions` transfers these amounts from the user via the `Accountant`. Crucially, **it never verifies if the final debt exceeds the original `maxAmount` parameters.**


### Impact
Users are exposed to unlimited slippage on their deposit inputs.
*   **Direct Financial Loss:** If the price moves unfavorably during the extension hook (e.g., a large TWAMM sell order executes), the user is forced to supply tokens at a highly disadvantageous exchange rate, often exceeding their authorized `maxAmount`.
*   **MEV Exposure:** Attackers can front-run deposits into TWAMM pools or other extension-enabled pools by ensuring a price-moving state change happens immediately before the user's deposit settles, effectively sandwiching the liquidity addition without the user's consent.
*   **Invariant Violation:** The `maxAmount` parameters act as a contractual limit which the protocol violates, breaking the intended slippage protection mechanisms.
