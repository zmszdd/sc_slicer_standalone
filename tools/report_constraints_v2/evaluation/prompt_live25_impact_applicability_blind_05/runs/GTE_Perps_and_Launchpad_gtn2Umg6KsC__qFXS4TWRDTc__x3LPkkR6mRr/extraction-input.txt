Rewards claims can be blocked and tokens stranded due to mismatched quote token in addRewards

## Finding Description
The addRewards function accepts two arbitrary token addresses and attempts to infer which one is the pool’s base (launch) asset by checking whether a rewards pool exists for token0; if not, it swaps the order and uses token1 as base. While this correctly detects the base asset, the function does not validate that the other token (the “quote” asset) actually matches the configured quote asset of the pool (rs.quoteAsset). It proceeds to:
- add pending quote rewards,
- increase totalPendingRewards for the user-supplied quote token address,
- and transfer that arbitrary quote token to the contract.

Later, when users claim, the distributor uses rs.quoteAsset (the pool’s configured quote token) to distribute quote rewards and to decrement totalPendingRewards for rs.quoteAsset. If the added quote rewards were funded with a different token address than rs.quoteAsset, the claim path attempts to decrement totalPendingRewards[rs.quoteAsset] which was never increased, causing ClaimAmountExceedsTotalPendingRewards and blocking claims. The mis-deposited token remains stuck in the contract.

Highest-impact scenario:
- Pool base = LToken, pool quote = USDC.
- A caller funds quote rewards using DAI via addRewards(LToken, DAI, 0, amount).
- The function accepts DAI, increases totalPendingRewards[DAI], and transfers DAI in.
- Any subsequent claim attempts to transfer USDC and decrement totalPendingRewards[USDC], which was not increased, triggering a revert and leaving the DAI stranded.

## Root cause:
In contracts/launchpad/Distributor.sol#L106-L131 the function accepts a user-supplied “quoteAsset” without enforcing that it equals the configured rs.quoteAsset for the base asset’s rewards pool. It then accounts pending rewards and transfers for the arbitrary quoteAsset instead of the canonical rs.quoteAsset, creating a mismatch between deposits and distribution accounting.
