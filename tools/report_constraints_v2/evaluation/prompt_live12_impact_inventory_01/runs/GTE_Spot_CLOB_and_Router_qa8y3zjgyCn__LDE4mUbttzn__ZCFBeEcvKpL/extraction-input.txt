FOK orders incorrectly revert due to lot size rounding, contradicting specification

## Finding description and impact
The vulnerability stems from how the contract handles the remaining "dust" from an order after it's been rounded down to the nearest lotSize. Here is the step-by-step flow that leads to the incorrect revert:

* User Action: A user calls `postFillOrder` to submit a Fill-or-Kill (FOK) order. Let's assume the market `lotSize` is 100 and the user wants to buy 199 units.

* Order Creation: The `_processFillBidOrder` function creates a temporary order in memory, `newOrder`, where `newOrder.amount` is 199.

* Matching Logic: This function then calls the internal matching logic (`_matchIncomingBid`), passing newOrder as an argument. Crucially, because [`newOrder`](https://github.com/code-423n4/2025-07-gte-clob/blob/main/contracts/clob/CLOB.sol#L347) is a memory struct, it's passed by reference, not as a copy. Any change to the order inside the matching logic will affect the original `newOrder`.

* Rounding: Inside the `_matchIncomingOrder` function, the code calculates the fillable amount, which is rounded down to the nearest `lotSize`.

    fillableAmount = (199 / 100) * 100 which results in 100.

* State Update: The matching logic then updates the amount of the user's order that is still left to be filled:

    - incomingOrder.amount -= fillableAmount; (which is 199 - 100).
    - Because `incomingOrder` is a reference to `newOrder`, the value of newOrder.amount is now updated to 99.

* Incorrect Revert: The matching logic finishes, and control returns to the `_processFillBidOrder` function. The code now performs the FOK check: [`if (... && newOrder.amount > 0)`](https://github.com/code-423n4/2025-07-gte-clob/blob/main/contracts/clob/CLOB.sol#L440).

    - Since `newOrder.amount` is now 99, the condition is true.
    - The transaction incorrectly reverts with `FOKOrderNotFilled()`, even though the only amount left unfilled was the dust from rounding, which the specification says should be ignored.
