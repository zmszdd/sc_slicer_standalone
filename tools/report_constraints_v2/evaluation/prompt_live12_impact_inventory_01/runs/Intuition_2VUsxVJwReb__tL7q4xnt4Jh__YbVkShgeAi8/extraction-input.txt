AtomWallet: ERC-4337 Storage Violation Bricks All Unclaimed Wallets

## Finding description and impact
`AtomWallet.owner()` at L271 has two branches:

`_validateSignature`, which is called by every `validateUserOp` execution, calls `owner()` at L309:

For every unclaimed AtomWallet, `validateUserOp` reads storage from MultiVault via the `getAtomWarden()` external call. This violates ERC-4337 §6.2.

The ERC-4337 bundler storage access rule (enforced via debug_traceCall simulation by Pimlico, Alchemy, Infinitism, and all compliant bundlers) states:

`During validateUserOp, an account may only access its own storage, or the storage of entities that are staked in the EntryPoint (paymasters, factories).`


`MultiVault` is not staked in the EntryPoint — it is a plain protocol contract. Any compliant bundler simulating the UserOp will detect that validateUserOp SLOAD'd from MultiVault's storage slot and reject the UserOp before it reaches the chain.

### Impact:

- Every AtomWallet is deployed in the unclaimed state. This means the entire protocol's ERC-4337 infrastructure is non-functional by default. The `atomWarden` cannot use UserOps to interact with unclaimed wallets through bundlers. Sponsored transactions, paymasters, and any bundler-based gas abstraction are unavailable until a wallet is individually claimed — which itself requires a direct on-chain transaction, defeating the purpose of the AA design.

The violation disappears post-claim because `isClaimed = true causes owner()` to read from the wallet's own local storage slot instead.
