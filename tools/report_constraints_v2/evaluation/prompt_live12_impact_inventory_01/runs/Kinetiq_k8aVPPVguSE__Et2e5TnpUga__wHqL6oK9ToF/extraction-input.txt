`StakingManager.sol` - `cancelWithdrawal` Fails to Remove Pending Withdrawal Operation from L1 Queue, Leading to State Inconsistency and Potential Value Imbalance

## Finding Description and Impact
**Description:**
The protocol's withdrawal process consists of three main steps:
1. Users lock their kHYPE by calling the `queueWithdrawal` function, calculate the corresponding HYPE amount, and add an L1 withdrawal operation (of type `OperationType.UserWithdrawal`) to the `_pendingWithdrawals` queue.
2. A role with the `OPERATOR_ROLE` calls the `processL1Operations` function, processing the operations in the `_pendingWithdrawals` queue, sequentially calling `l1Write.sendTokenDelegate(..., true)` and `l1Write.sendCWithdrawal(...)` for each operation to complete the undelegation and fund transfer on L1.
3. After a specified delay period, users call the `confirmWithdrawal` function, verifying that the L1 operation has completed by checking the status of `_withdrawalRequests`, then burning the kHYPE and transferring the HYPE to the user.

In addition, the protocol allows a role with the `MANAGER_ROLE` to cancel a user's withdrawal request by calling the `cancelWithdrawal` function. This function performs the following operations:
- Deletes the relevant record in `_withdrawalRequests`;
- Returns the locked kHYPE (including fees) to the user;
- Accumulates the cancelled HYPE amount (after deducting fees) to `_cancelledWithdrawalAmount` for subsequent redelegation.

However, **the `cancelWithdrawal` function has a critical flaw: it does not remove the corresponding L1 withdrawal operation from the `_pendingWithdrawals` queue.**

**Impact:**
This flaw leads to severe state inconsistency and potential value imbalance problems, specifically:
1. **The L1 Withdrawal Operation Will Still Be Executed:**
    Although the withdrawal request on L2 has been cancelled and the user has retrieved their kHYPE, the existing L1 withdrawal operation in the queue will still be executed as long as the `OPERATOR_ROLE` calls `processL1Operations`. This means that HYPE will be undelegated from the L1 validator and transferred as usual (potentially eventually returning to the `StakingManager`'s L2 contract).

2. **Double Counting and Value Imbalance:**
    - The user has recovered their kHYPE;
    - The protocol still executes the HYPE withdrawal from L1;
    - The protocol records a portion of the HYPE value (`hypeAmount`) in `_cancelledWithdrawalAmount` and plans to redelegate it.
    This effectively causes the same cancelled withdrawal to be processed twice: once to return the kHYPE to the user, and once to withdraw the HYPE from L1. This operation breaks the value balance between HYPE and kHYPE.

3. **Confused Protocol Funds State:**
    After the L1 withdrawal is complete, the HYPE returns to L2 (assuming the mechanism works correctly), but this HYPE no longer has a corresponding kHYPE liability (because the kHYPE has been returned to the user). At the same time, the amount recorded in `_cancelledWithdrawalAmount` is planned to redelegate a portion of the value. This creates confusion in the relationship between the protocol's HYPE holdings and the total kHYPE supply, causing the exchange rate calculated by the `StakingAccountant` to deviate significantly from reality.

4. **Potential Exploitation Risks:**
    Although no direct fund theft path has been discovered yet, this state of confusion and value imbalance could be exploited by attackers familiar with the protocol mechanism. For example, by manipulating the timing of cancellations and processing, combined with a distorted exchange rate, attackers may find arbitrage opportunities or extract additional value from the protocol.
