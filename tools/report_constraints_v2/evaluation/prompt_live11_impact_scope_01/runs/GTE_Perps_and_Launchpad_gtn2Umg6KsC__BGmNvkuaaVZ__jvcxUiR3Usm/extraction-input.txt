Balances accounting bug in GTELaunchpadV2Pair leads to stealing of locked assets

## Summary

The `GTELaunchpadV2Pair` contract contains critical accounting bugs in its `mint()`, `swap()`, and `burn()` functions. These functions fail to properly account for accrued launchpad fees when calculating token amounts, allowing attackers to steal locked assets from the pair.

## Finding Impact

**Impact: High**

The impact is high because:

1. The vulnerability allows attackers to steal locked assets (both token0 and token1) from any `GTELaunchpadV2Pair` with rewards accrual enabled.
2. This affects all pairs for the launchpad's launch-quote asset pools for all graduated launch tokens.
3. The vulnerability can be silently exploited repeatedly until all locked assets are drained.
4. The attack can drain the entire liquidity pool over time, causing direct financial loss to token launchers (projects partnering with GTE) and other liquidity providers.

## Finding Likelihood

**Likelihood: High**

The likelihood is high because:

1. The attack requires minimal resources - only gas fees to call `mint()`, `swap()`, or `burn()` on the target pair.
2. No special conditions need to be met beyond the pair having accrued some fees, which attackers can generate themselves.
3. The attack can be executed by any external user without special permissions.
4. The vulnerability is present in core functions that are frequently used. This means that the issue can be accidentally triggered even when the functions are called by normal users (the most likely functions are `mint()` and `burn()`).
5. The vulnerability affects all pairs that enable rewards accrual (i.e., all pairs for graduated launch tokens), making it widespread across the protocol.

## Finding Description

The `GTELaunchpadV2Pair` contract contains accounting bugs in three key functions: `mint()`, `swap()`, and `burn()`. These functions fail to properly account for accrued launchpad fees (`accruedLaunchpadFee0` and `accruedLaunchpadFee1`) when calculating token amounts.

### Issue 1: Incorrect calculation in `mint()`

In the `mint()` function, the calculation of `amount0` and `amount1` does not account for accrued launchpad fees:


The issue arises because `_reserve0` and `_reserve1` already account for `accruedLaunchpadFee0` and `accruedLaunchpadFee1` (as you can see in the `_update()` function in the `Root Cause` section below), while `balance0` and `balance1` can contain these accrued fees. This means that if there are no token transfers into the pair, `amount0` will equal `accruedLaunchpadFee0` and `amount1` will equal `accruedLaunchpadFee1`, allowing an attacker to mint liquidity for free.

Furthermore, the issue in this function can even be accidentally triggered when normal users call it.

### Issue 2: Incorrect calculation in `swap()`

In the `swap()` function, there are two related issues:

1. Incorrect calculation of `amount0In` and `amount1In`
2. Incorrect calculation of `balance0Adjusted` and `balance1Adjusted`


Similar to the `mint()` function, `_reserve0` and `_reserve1` already account for accrued fees, while `balance0` and `balance1` can contain these fees. This means that if there are no token transfers into the pair, `amount0In` will equal `accruedLaunchpadFee0 + amount0Out` and `amount1In` will equal `accruedLaunchpadFee1 + amount1Out`.

Moreover, the calculation of `balance0Adjusted` and `balance1Adjusted` also fails to account for accrued fees. They can contain larger values than expected because `balance0` and `balance1` may contain accrued fees. As a result, an attacker can swap out tokens for free without transferring in any tokens.

### Issue 3: Incorrect calculation in `burn()`

In the `burn()` function, the calculation of `amount0` and `amount1` also fails to account for accrued fees:


Since `balance0` and `balance1` can contain accrued fees, this results in transferring out more tokens than expected, allowing an attacker to extract more value than they should be entitled to.

Furthermore, the issue in this function can even be accidentally triggered when normal users call it.

The root cause of these issues is that the `_update()` function in `GTELaunchpadV2Pair` subtracts accrued fees from balances when calculating reserves:


However, the `mint()`, `swap()`, and `burn()` functions do not properly account for this when calculating token amounts, leading to the vulnerabilities described.
