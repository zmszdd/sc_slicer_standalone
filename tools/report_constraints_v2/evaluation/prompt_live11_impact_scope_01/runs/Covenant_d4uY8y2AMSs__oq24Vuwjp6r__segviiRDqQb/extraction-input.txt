noCapLimit default applied to baseToken, not quoteToken (policy confusion)

## Finding description and impact

LatentSwapLEX exposes `setDefaultNoCapLimit(address token, uint8)` documented as: “if defaultMintRedeemNoCap == 0, new markets will use 1 baseToken as the MintRedeemNoCap as the default” and “for markets with this quote token”. At init, the code reads `tokenNoCapLimit[marketParams.baseToken]` and assigns that to the market’s `noCapLimit`. This creates a policy confusion: governance expecting to configure the default mint/redeem cap for “markets with this quote token” by calling `setDefaultNoCapLimit(quoteToken, x)` will have no effect. Only overrides set for the baseToken address are used. As a result, markets instantiated under a given quote do not inherit the intended cap setting, potentially leaving large markets unbounded or overly restricted depending on expectation.


Misconfiguration risk: quote-level policy changes are silently ignored. Operators can believe caps are set for an entire quote currency class when in fact they are not, leading to unintended liquidity growth or unnecessary constraints.
