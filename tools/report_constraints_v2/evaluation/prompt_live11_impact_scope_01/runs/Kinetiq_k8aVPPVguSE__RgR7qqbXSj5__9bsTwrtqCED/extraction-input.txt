Front-Running Reward and Slashing Events to Exploit Exchange Ratio Calculations

## Finding description and impact

The protocol’s conversion of HYPE to kHYPE relies on an exchange ratio computed in `StakingAccountant::_getExchangeRatio` based on the aggregate of the total staked amount, rewards, claimed funds, and slashing amounts as reported by the `ValidatorManager`. Because the rewards and slashing amounts are read on demand from an external source, an attacker can front-run rewards and slashing events and potentially game the system.

If rewards are accredited in intervals longer than `StakingManager::withdrawalDelay`, attackers can exploit front-running reward events. If staked amounts are sufficiently large, front-running slashing event is always profitable as the cost of calling the `queueWithdrawal` is lower than the penalty avoided.

For example:
 - When a rewards event is about to be recorded, the exchange ratio (totalHYPE/totalKHYPESupply) is lower since the rewards have not yet been added. Users can just wait for the reward event to occur to front-run it and `stake` and receive the rewards instead of staking in the intended way.

 - Conversely, a user can front-run the slashing event and `queueWithdrawal` the funds to avoid the penalization.

Users are incentivized to stake immediately before rewards events occur, which undermines the protocol’s intended distribution of rewards. Similarly, users could `queueWithdrawal` their funds just prior to a slashing event to avoid incurring the associated penalties, compromising the protocol’s fairness and stability.

For sufficiently large amounts, exploiting this vulnerability can yield significant profits.
