Improper addition of new orders to the order book leads to lost and unfillable orders.

## Finding description and impact
In Book.sol, the function [addOrderToBook()](https://github.com/code-423n4/2025-07-gte-clob/blob/92a8839e3eb9715d53e24f0168442cecdc9b784b/contracts/clob/types/Book.sol#L150) is called to add limit orders to the book. This function calls two other functions, _updateBookPostOrder and _updateLimitPostOrder

In [_updateBookPostOrder](https://github.com/code-423n4/2025-07-gte-clob/blob/92a8839e3eb9715d53e24f0168442cecdc9b784b/contracts/clob/types/Book.sol#L256-L270), the price is added to the tree, the book's metadata is updated, and the order is added to storage.
In [_updateLimitPostOrder](https://github.com/code-423n4/2025-07-gte-clob/blob/92a8839e3eb9715d53e24f0168442cecdc9b784b/contracts/clob/types/Book.sol#L281), the limit for the price is updated, adding the new order and updating the previous and next order id to ensure orderliness of the orders.
The `issue` here is that after the `order` has already been added to storage in _updateBookPostOrder.
_updateLimitPostOrder is called, and the order passed into _updateLimitPostOrder is of type `memory`, therefore, when the `prevOrderId` for the new order is updated, this only happens to the order passed in and not the one in storage.
In solidity, once a value in `memory` is saved to `storage`, any further changes to that memory value do `not` reflect in storage. The value in storage stays the same as when it was first stored.

## impact

This means all the orders added to the book do not have their `prevOrderId` saved with them.
This will severely disrupt the orderliness of the book, leading to orders becoming lost in the book and can never be filled. 

When, for any reason, an order is removed, it is assumed to be the head and the next order is made the new head of the orders in the price limit.
Example, lets say there are ten order in a particular limit, then the seventh order is removed, since its `prevOrderId` does not exist (is null) the function `_updateLimitRemoveOrder` will treat it as the first order in the price limit and set its next id as the new head of the limit, leaving the first six orders lost and unable to be fulfilled.
