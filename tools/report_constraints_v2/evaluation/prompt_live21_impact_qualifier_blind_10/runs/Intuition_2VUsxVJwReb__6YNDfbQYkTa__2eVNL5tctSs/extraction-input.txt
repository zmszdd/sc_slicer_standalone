AtomWallet signature time-window (validUntil/validAfter) can be trivially bypassed by stripping the 12-byte suffix

## Vulnerability details

##  Description

  The _validateSignature function in AtomWallet implements an optional time-window mechanism via validUntil and validAfter fields appended as a 12-byte suffix to the ECDSA signature. The contract accepts two
  signature formats:

  - 65 bytes (r | s | v): interpreted as having no time restrictions (validUntil=0, validAfter=0)
  - 77 bytes (r | s | v | validUntil | validAfter): parsed for time-window enforcement

  The critical flaw is that the ECDSA signature covers only the userOpHash — the 12-byte time-window suffix is not included in the signed message. This means the suffix can be freely stripped or modified by any
  third party without invalidating the cryptographic signature.

  At line 297, the signed hash is derived exclusively from userOpHash:

  bytes32 hash = keccak256(abi.encodePacked("\x19Ethereum Signed Message:\n32", userOpHash));

  The userOpHash is computed by the EntryPoint from the PackedUserOperation fields, but per ERC-4337 specification, the signature field itself is excluded from this hash. Therefore, the time-window bytes appended
  inside the signature are never covered by any cryptographic commitment.

  At lines 343-344, the extraction function treats a 65-byte signature as unrestricted:

  if (signatureLength == 65) {
      return (0, 0, signature); // validUntil=0 means no expiry, validAfter=0 means immediately valid
  }

  Any observer who sees a 77-byte time-restricted signature can truncate the last 12 bytes, producing a valid 65-byte signature that the contract accepts with zero time restrictions.

## Impact

  - Time-locked operations become permanently executable. An owner who intends a transaction to be valid only within a narrow window (e.g., 5 minutes) loses that guarantee entirely. The operation can be executed
  at any arbitrary future time.
  - Delayed execution attacks. A malicious bundler or MEV searcher can hold the stripped-signature UserOperation and execute it at the most disadvantageous moment — after a price movement, governance vote, access
  revocation, or other state change the owner was trying to time-bound against.
  - Breaks security model for all AtomWallets. Since AtomWallets are created per-atom and manage protocol assets across the Intuition ecosystem, the ability to bypass time restrictions impacts fund safety for
  every atom.
  - Not theoretical. ERC-4337 UserOperations are broadcast through an alt-mempool where bundlers and searchers routinely inspect, reorder, and modify operations before inclusion. The signature field is fully
  visible and trivially modifiable.

##   Attack Scenario

  1. Wallet owner creates a time-restricted UserOperation (e.g., valid only between 14:00–14:05 UTC) and signs a 77-byte signature: [r(32) | s(32) | v(1) | validUntil(6) | validAfter(6)]
  2. The UserOperation enters the ERC-4337 alt-mempool awaiting bundler inclusion
  3. A malicious bundler or MEV searcher extracts the 77-byte signature, truncates it to 65 bytes (removing the time-window suffix), and replaces userOp.signature with the shortened version
  4. The contract's _extractValidUntilAndValidAfterFromSignature sees a 65-byte signature and returns (validUntil=0, validAfter=0) — no time restriction
  5. _validateSignature recovers the same signer (since the ECDSA bytes are identical) and returns _packValidationData(false, 0, 0)
  6. The EntryPoint accepts the operation at any time, completely bypassing the owner's intended time window
