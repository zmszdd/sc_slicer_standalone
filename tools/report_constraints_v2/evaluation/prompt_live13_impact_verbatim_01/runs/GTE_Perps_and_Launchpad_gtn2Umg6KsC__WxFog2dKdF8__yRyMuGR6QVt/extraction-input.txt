Init Code Hash Mismatch between `Launchpad::pairFor` and `GTELaunchpadV2PairFactory::createPair`  Causes Incorrect Pair Address Calculations Leading to complete brick of Token Graduation Process and Funds Lock Risk

### Description

The vulnerability stems from a salt mismatch between how pairs are created vs. how their addresses are calculated:

- The [`GTELaunchpadV2PairFactory::createPair`](https://github.com/code-423n4/2025-08-gte-perps/blob/f43e1eedb65e7e0327cfaf4d7608a37d85d2fae7/contracts/launchpad/uniswap/GTELaunchpadV2PairFactory.sol#L39-L42) uses the actual bytecode hash for `CREATE2` calculations when deploying pairs.

- The [`Launchpad::pairFor`](https://github.com/code-423n4/2025-08-gte-perps/blob/f43e1eedb65e7e0327cfaf4d7608a37d85d2fae7/contracts/launchpad/Launchpad.sol#L579) function uses `uniV2InitCodeHash` in the keccak256 hash:



### This results in several issues

1. Different Salt Calculations: The factory uses a 4-parameter salt (token0, token1, launchpadLp, launchpadFeeDistributor) while pairFor() only uses 2 parameters (token0, token1).

2. Address Mismatch: This causes pairFor() to calculate a completely different CREATE2 address than where the pair is actually deployed.

3. Guaranteed Failure: In `_createPairAndSwapRemaining()`, the code calls


This will always revert because it's calling `skim()` on a non-existent contract.

### The `uniV2InitCodeHash` Red Herring
The document mentions `uniV2InitCodeHash` being uninitialized, but that's actually a secondary issue. The primary problem is the salt mismatch. Even if `uniV2InitCodeHash` were correctly set, the wrong salt would still cause address calculation failures.

### Impact
This is a High severity vulnerability because:

- It affects core functionality (token graduation)
- No external attacker needed - fails on normal operations
- Permanent DoS - tokens get stuck in bonding phase
- Affects all users attempting to graduate tokens




5. All Graduations Fails: Every token graduation will fail when it reaches the liquidity addition phase, regardless of whether an attacker is involved.

### Verification
Looking at the `GTELaunchpadV2PairFactory::createPair` code, when msg.sender == launchpad, it uses the full 4-parameter salt. But pairFor() in the Launchpad only uses 2 parameters, so they'll never match.


### Recommended Mitigations
1. Align Salt Calculation Between GTELaunchpadV2PairFactory and Launchpad

- The pairFor() in Launchpad.sol must use the exact same salt that GTELaunchpadV2PairFactory::createPair uses.

- That means including both launchpadLp and launchpadFeeDistributor in the abi.encodePacked() inside pairFor():


2. This ensures that pairFor() and createPair() always resolve to the same address.

- Remove Redundant `uniV2InitCodeHash`

- Right now Launchpad::pairFor uses a uniV2InitCodeHash that’s never set → misleading and brittle.

- Instead, calculate the init code hash directly from the `GTELaunchpadV2Pair` creation code `(keccak256(type(GTELaunchpadV2Pair).creationCode))`, just like Uniswap does in its periphery.

This makes the calculation self-contained and removes reliance on external config.
