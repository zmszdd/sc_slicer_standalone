Proxy initialization can be frontrun allowing attacker to gain full control over deployed contracts

## Description:

The `Distributor` and `DistributionCreator` contracts inherit from `UUPSHelper`, which uses an outdated initialization protection pattern:


This pattern, while functional, has two critical weaknesses:

1. OpenZeppelin recommends using `_disableInitializers()` in constructors since version 4.6.0+ for more robust and explicit protection of implementation contracts.

2. The contracts are designed to be deployed as UUPS proxies that require a separate `initialize()` call after proxy deployment. When proxies are deployed with empty initialization data and then initialized in a subsequent transaction, this creates a frontrunning window where an attacker can call `initialize()` with malicious parameters before the legitimate deployer.

The vulnerability exists in both `Distributor.sol` and `DistributionCreator.sol`, as both:
- Use `constructor() initializer {}` pattern
- Have public `initialize()` functions with no access control (by design of the initializer pattern)
- Are intended to be deployed behind UUPS proxies

The protocol's deployment script (`merklDeploy.s.sol`) uses a vulnerable pattern for deploying and initializing UUPS proxies.

## Scenario:

1. Deployer creates a new `ERC1967Proxy` pointing to `Distributor` implementation with empty initialization data
2. Proxy is deployed but remains uninitialized (vulnerable state)
3. Attacker monitoring the blockchain/mempool detects the uninitialized proxy
4. Attacker frontruns the legitimate `initialize()` call with their own transaction
5. Attacker passes a malicious `IAccessControlManager` where they control the governor role
6. Attacker's `initialize()` executes first, successfully taking control
7. Legitimate `initialize()` transaction reverts with "Initializable: contract is already initialized"
8. Attacker now controls the proxy via their malicious access control manager
9. Attacker can execute governor-only functions:
   - `toggleTrusted()` to grant themselves trusted status
   - `updateTree()` to manipulate reward distributions
   - `recoverERC20()` to steal all funds from the contract
   - Modify critical parameters (dispute settings, fees, etc.)


## Impact:

Complete compromise of protocol ownership and funds. An attacker who successfully frontruns initialization gains full administrative control over `Distributor` and/or `DistributionCreator` contracts
