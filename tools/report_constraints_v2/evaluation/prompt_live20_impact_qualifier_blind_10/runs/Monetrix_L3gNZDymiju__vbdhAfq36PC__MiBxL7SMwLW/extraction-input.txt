`0x811` borrow fields are ignored, so PM liabilities overstate backing and admit unbacked yield

## Summary

Monetrix treats HyperCore precompile `0x811` as a supply-only balance source, but Hyperliquid's official `L1Read.sol` defines `0x811` as a borrow-lend user-state object containing **both** `borrow` and `supply` values for a token.

`PrecompileReader.suppliedBalance()` decodes the four `uint64` words returned by `0x811` and keeps only the last one. As a result:

- PM-supplied collateral is counted into backing
- PM borrow liabilities are never subtracted

This lets `totalBackingSigned()` and `surplus()` become positive even when the true PM net state is negative. Once that happens, `settle()` can admit yield that should have been blocked by Gate 3, and `distributeYield()` can route that unbacked value to stakers / insurance / foundation.


Hyperliquid's official [`Interacting with HyperCore`](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/hyperevm/interacting-with-hypercore) docs ship an attached `L1Read.sol` that defines `0x811` as:


So the `0x811` payload is not "supplied amount only." It is:

1. `borrow.basis`
2. `borrow.value`
3. `supply.basis`
4. `supply.value`

That drops the entire borrow side by construction.

There is no corresponding subtraction of `borrow.value`.

This becomes exploitable in normal PM flows:

1. the Vault supplies collateral under PM, e.g. through `executeHedge()` or `supplyToBlp()`
2. PM auto-borrow / borrow-lend state creates a negative quote liability
3. Monetrix counts the supplied collateral through `0x811`
4. Monetrix does **not** subtract the PM borrow side from the same official precompile state
5. `surplus()` becomes overstated
6. `settle()` accepts yield that should have failed the distributable-surplus gate
7. `distributeYield()` routes real value out based on that phantom surplus

This is not an offchain monitoring issue. The onchain safety gate itself is reading the borrow-lend state incorrectly.

## Impact

This breaks the protocol's core backing invariant for PM accounts.

The concrete sink is false-positive yield settlement:

- the protocol believes backing exceeds liabilities
- `settleDailyPnL()` therefore accepts a `proposedYield`
- `settle()` moves real USDC into `YieldEscrow`
- `distributeYield()` then:
  - mints fresh `USDM` into `sUSDM` for the user share
  - routes the insurance share into `InsuranceFund`
  - routes the foundation share to the foundation

So a PM borrow that should have reduced backing can instead be ignored while yield is distributed as if the protocol were solvent.

This is Medium:

- It is an accounting defect in a core value-measurement path
- It admits value distribution that should have been blocked by the onchain settlement guard
