Reentrancy / accounting before transfer in Distributor.addRewards — attacker can re-enter and observe/act on updated accounting

## Finding description and impact

Distributor.addRewards updates internal pending-reward accounting before performing the external transferFrom call. A malicious token can re-enter during transferFrom and call claimRewards (or other entrypoints) while accounting has already been increased, producing a clear reentrancy window that can be used for griefing and, in some scenarios, monetary extraction.

Attackers can force the code path to re-enter claimRewards during addRewards, demonstrating an exploitable reentrancy window. This enables griefing and may be combined with other weaknesses to steal tokens.


If auth checks in claimRewards change or are relaxed in upgrades, the addRewards entrypoint becomes a        direct path for unauthorized forced liquidations/withdrawals or reward theft.

Direct ability to manipulate reward accounting and to re-enter core flows is High.

## Recommended mitigation steps
1) Use OpenZeppelin ReentrancyGuard (or similar) At top of Distributor.sol

   Add nonReentrant modifier to external functions that perform transfers and state changes:

   function addRewards(...) external nonReentrant {
    ...
}
function claimRewards(...) external nonReentrant {
    ...
}

2) Move transferFrom before bookkeeping (preferred order)
