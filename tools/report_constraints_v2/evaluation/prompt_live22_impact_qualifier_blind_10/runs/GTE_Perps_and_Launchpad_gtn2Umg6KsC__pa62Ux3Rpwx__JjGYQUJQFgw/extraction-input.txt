Error in ClearingHouse’s _movePop can Lead to Wrong Positions and Liquidations

## Finding description and impact

The `_movePop` helper function in ClearingHouse.sol contains an implementation error that corrupts the asset tracking system when users close positions. Instead of removing the closed position's asset from the memory array, it incorrectly removes the last asset in the array while leaving the target asset in place. This desynchronization between memory and storage states causes the protocol to fetch wrong positions for calculations.

The `_movePop` function is responsible for removing assets from a user's position array when they fully close a position. Let's understand the context first: when a user trades perpetual futures on GTE, the protocol tracks their positions across multiple assets using both a memory array and a storage set. These two data structures must remain synchronized for the protocol to correctly calculate margins, check liquidation thresholds, and manage collateral.

The bug occurs in the implementation of the swap-and-pop pattern.


The function intends to remove a specific asset from the array by moving the last element to fill the gap, then removing the now-duplicate last element. However, this line, `array.set(index, asset)` sets the element at the target index to itself, which does nothing. The correct implementation should move the last element to the target position: `array.set(index, array.get(array.length() - 1))`.

When a position is fully closed (amount becomes 0), the function calls `_movePop` to remove the asset from the memory array. Due to the bug, the wrong asset gets removed. Subsequently, `setAssets` is called with the corrupted array length and the correct asset to remove, creating a mismatch between what's in memory and what's in storage.

To illustrate with a concrete example: if a user has positions in [BTC, ETH, SOL] and closes their ETH position, the buggy `_movePop` function will set ETH to ETH at index 1 (no change), then pop the array, removing SOL instead. The memory array becomes [BTC, ETH] while the storage correctly removes ETH, leaving [BTC, SOL]. This desynchronization means subsequent operations will fetch ETH's position data (which is now zero) when they should be fetching SOL's active position.

When the memory array contains the wrong assets, the protocol calculates incorrect unrealized profit and loss (PnL) values.

Also, the protocol might incorrectly liquidate a healthy account because it's not accounting for profitable positions that got incorrectly removed from tracking. Conversely, it might fail to liquidate underwater positions because it's checking closed positions instead of active ones with losses.
