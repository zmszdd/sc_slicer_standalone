min_threshold_checked_on_gross_not_net

**Unit Name:** `DistributionCreator`

**Location:** `DistributionCreator.sol` - function `_createCampaign` (uses `_computeFees` and `_pullTokens`)

**Description:** 
The minimum reward-per-epoch check uses the gross `newCampaign.amount` before fees: `(newCampaign.amount * HOUR) / newCampaign.duration < rewardTokenMinAmount` reverts only if the pre-fee rate is too low. Immediately after, fees are deducted and `newCampaign.amount` is overwritten with `campaignAmountMinusFees`, which is the actual distributed amount. This allows campaigns whose NET per-epoch amount falls below `rewardTokenMinAmounts[token]`, violating the intended invariant “minimum per-epoch reward for validity.” Attackers can pass the check by supplying a large gross amount and a high fee rebate configuration that reduces the net amount below the threshold. Validate against post-fee amounts (or recompute threshold after fees) to preserve campaign validity guarantees.

**PoC Summary:** `test/poc/DistributionCreator_min_threshold_checked_on_gross_not_net.t.sol` — The test creates a 1-hour campaign whose gross amount passes `_createCampaign`’s per-epoch check but, after 50% fees, the net-per-epoch falls below `rewardTokenMinAmounts`, expecting a revert with `Errors.CampaignRewardTooLow`; since the contract validates the minimum on gross before fees, `createCampaign` does not revert, causing the test to fail and confirming the bug. Verdict: true positive.
