Division by zero in `executeWithdrawal` leads to permanently locked funds

## Finding description and impact

### Summary

A missing check in the `HypoVault.executeWithdrawal` function allows a division by zero to occur if a withdrawal epoch is fulfilled with zero shares. A manager can trigger this condition (intentionally or accidentally) by calling `fulfillWithdrawals` with `sharesToFulfill = 0`. This creates a broken state for that epoch where all pending user withdrawals become permanently locked. Affected users cannot execute their withdrawals, as the transaction will always revert, nor can they cancel them, as the cancellation function only operates on the current epoch. This results in a permanent loss of access to user funds for that epoch unless a complex manual intervention is performed by the owner.

### Root Cause

The vulnerability stems from a sequence of events across three functions:

1.  **`fulfillWithdrawals`:** In `src/HypoVault.sol`, the manager can call this function with `sharesToFulfill = 0`. The function will execute successfully, advancing the `withdrawalEpoch` but setting `withdrawalEpochState` for the just-closed epoch with `sharesFulfilled = 0`.
2.  **`executeWithdrawal`:** In `src/HypoVault.sol`, when a user tries to process a withdrawal from this broken epoch, the function attempts to calculate `assetsToWithdraw` using `Math.mulDiv(..., ..., _withdrawalEpochState.sharesFulfilled)`. Since `sharesFulfilled` is `0`, this call results in a division by zero, causing the transaction to revert.
3.  **`cancelWithdrawal`:** In `src/HypoVault.sol`, this function only operates on the *current* `withdrawalEpoch`. It cannot be used to cancel a withdrawal request that is stuck in a *previous* epoch.

#### Internal Pre-conditions

1.  A user has a pending withdrawal request in an active withdrawal epoch, `E`.
2.  The vault `manager` calls `fulfillWithdrawals` for epoch `E`, passing `sharesToFulfill = 0`.

### External Pre-conditions

1.  A user must have previously called `requestWithdrawal`.

### Attack Path

This bug can be triggered by a malicious or mistaken manager:
1.  A user, Alice, has shares in the vault and calls `requestWithdrawal(amount)` during epoch `E`.
2.  The `manager` calls `fulfillWithdrawals(0, ...)`. This closes epoch `E`, setting `sharesFulfilled` for it to `0`, and advances the active withdrawal epoch to `E+1`.
3.  Alice calls `executeWithdrawal(Alice, E)` to process her pending request.
4.  The call to `Math.mulDiv` inside `executeWithdrawal` reverts with a panic code `0x12` (division by zero).
5.  Alice's withdrawal is now stuck. She cannot successfully call `executeWithdrawal` for epoch `E`.
6.  She also cannot call `cancelWithdrawal`, as it would only apply to a request in the current epoch, `E+1`.
7.  **Outcome:** Alice's funds associated with the withdrawal request in epoch `E` are permanently locked and cannot be retrieved via the standard contract functions.

### Recommendations

The vulnerability can be fixed by adding a zero-check in `executeWithdrawal` before the `Math.mulDiv` call. This handles the edge case gracefully by recognizing that if zero shares were fulfilled, zero assets should be disbursed, and allows the remaining logic (which moves the request to the next epoch) to proceed without reverting.


This change should replace the original single-line `assetsToWithdraw` calculation.
