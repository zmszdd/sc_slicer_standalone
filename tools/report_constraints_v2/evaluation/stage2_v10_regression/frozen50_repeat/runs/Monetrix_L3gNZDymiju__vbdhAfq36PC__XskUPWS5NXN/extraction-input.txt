Borrow leg of 0x811 (BORROW_LEND_USER_STATE) is silently discarded, allowing phantom surplus to drain principal as yield once Vault has any PM auto-borrow position

## Background

HyperLiquid's `0x0000…0811` precompile is `BORROW_LEND_USER_STATE_PRECOMPILE_ADDRESS` (per `hyperliquid-dev/hyper-evm-lib/src/PrecompileLib.sol` and the official `L1Read.sol`). It returns the struct:

    struct BorrowLendUserTokenState {
        BasisAndValue borrow;   // borrow.basis (uint64), borrow.value (uint64)
        BasisAndValue supply;   // supply.basis (uint64), supply.value (uint64)
    }

— ABI-encoded as four sequential `uint64` slots: `(borrow.basis, borrow.value, supply.basis, supply.value)`.

`borrow.value` is outstanding debt (principal + accrued interest); `supply.value` is the user's lent balance. For solvency accounting, both legs matter: a user with `supply.value=60k` and `borrow.value=40k` has net BLP exposure of `+20k`, not `+60k`.

Per HyperLiquid's official Portfolio Margin docs, once PM is enabled on a Vault account, borrows happen automatically — pure adverse price movement against existing collateral is enough to trigger an auto-borrow. No operator action required.

## Root cause

`PrecompileReader.suppliedBalance` only reads the fourth uint64 slot:

    function suppliedBalance(address account, uint64 token) internal view returns (uint64 supplied) {
        (bool ok, bytes memory res) = PRECOMPILE_SUPPLIED_BALANCE.staticcall(abi.encode(account, token));
        require(ok, "supplied: precompile failed");
        require(res.length >= 128, "supplied: bad len");
        (,,, supplied) = abi.decode(res, (uint64, uint64, uint64, uint64));
        // ^^^ borrow.basis, borrow.value, supply.basis discarded
    }

A repo-wide grep `grep -rn "borrow" src/` confirms there is **zero** code anywhere in scope that reads `borrow.basis` or `borrow.value` — neither `PrecompileReader`, `MonetrixAccountant`, `MonetrixVault`, nor `TokenMath`.

Consequently `MonetrixAccountant._readL1Backing` sums:

    perp accountValue + L1 spot USDC + Σ supply.value + Σ spot hedge × oraclePx + HLP equity

`borrow.value` is never subtracted. Once an auto-borrow triggers, `totalBackingSigned()` overstates real net assets by exactly the borrow amount.

## Invariants violated

- INV-1 (peg solvency) — reported backing > real backing
- INV-7 (Gate 3 distributable cap) — phantom surplus passes the gate
- INV-9 (Σ proposedYield ≤ Σ surplus) — `settle` accepts unbacked yield

## Attack flow

1. Vault is in production with USDM minted 1:1 against USDC. PM is activated on the Vault's L1 account.
2. Vault opens a hedge or carries a spot position. HyperLiquid's PM auto-borrow triggers due to adverse price movement (e.g. BTC drops). The Vault's L1 account now shows: spot USDC = +X, 0x811 borrow.value = +X. Real net assets unchanged.
3. The Operator's keeper computes `surplus()` from on-chain state. The Accountant reports `surplus = +X` (the borrow leg is invisible). The keeper proposes yield up to this phantom surplus.
4. `vault.settle(proposedYield)` passes Gate 3 (because reported `distributableSurplus > 0`) and Gate 4 (annualized cap, easy to stay under for moderate amounts), then transfers `proposedYield` USDC from the Vault's principal pool to YieldEscrow.
5. `distributeYield` routes that USDC to sUSDM stakers (mints USDM yield), InsuranceFund, and Foundation. The principal that backed USDM is now permanently displaced.

The attack does not require Operator collusion — a buggy or rational keeper that trusts on-chain `surplus()` will mechanically propose phantom yield.

## Verification of the precompile layout

Decoding can be cross-checked against an actual mainnet API response. HyperLiquid's `clearinghouseState` for any user with active BLP positions returns entries like:

    "borrow": {"basis": "10.00000000", "value": "10.04217650"},
    "supply": {"basis": "44.69295862", "value": "44.69692314"}

— `value > basis` confirms `value = principal + accrued interest`. Both legs are present in the precompile response; the contract only consumes one.
