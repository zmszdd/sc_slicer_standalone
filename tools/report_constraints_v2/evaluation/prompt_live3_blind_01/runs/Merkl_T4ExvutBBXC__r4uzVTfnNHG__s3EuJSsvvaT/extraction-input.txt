Empty Catch Block Silently Swallows Reverting Callbacks, Bypassing Intended Validation

### Finding description and impact

The `_claim()` function in Distributor.sol uses a try-catch block to handle callbacks to `IClaimRecipient.onClaim()`. However, the catch block is empty, causing all reverts from the callback to be silently ignored. This allows claim recipients to bypass intended validation logic or access control checks that should be enforced through the callback mechanism.

## Distinction from V12-M-01

V12-M-01 identified that the try/catch block in `_claim()` has asymmetric error handling, focusing on how wrong return values inside the try block cause uncaught reverts that DoS entire claim batches.

This finding demonstrates the **opposite vulnerability**: when the callback itself reverts (before returning a value), the empty catch block silently swallows the error, allowing the claim to succeed even when validation should have prevented it.

**Attack Vector Comparison:**
- **V12-M-01:** Success path with wrong return → Revert inside try → Uncaught → DoS batch
- **This Finding:** Failure path with revert → Caught by empty catch → Silently ignored → Bypass validation

While both findings stem from the same asymmetric try/catch implementation at lines 482-485, they enable distinct exploits with opposite impacts: V12 shows how it causes DoS, this shows how it enables bypasses.

### Concrete Example: Rate Limiting Bypass

Consider a recipient contract that implements daily claim limits to prevent abuse:


**Attack Scenario:**
1. Alice sets RateLimitedRecipient as her claim recipient
2. Malicious operator attempts to claim 2000 tokens for Alice
3. Callback executes: `dailyClaimed[alice] + 2000 > 1000` → reverts
4. **Empty catch block swallows the revert**
5. Claim proceeds successfully
6. Alice receives 2000 tokens despite 1000 token daily limit

**Impact:** The rate limiting validation is completely bypassed, allowing operators to exceed intended limits.

**Why This is NOT a V12 Duplicate:**

V12-M-01 identifies "Improper Error Handling of onClaim Callback" focusing on wrong return values **reverting the entire batch**. This finding demonstrates the **opposite problem**: reverting callbacks are silently ignored, allowing claims to succeed when they should fail. These are distinct attack vectors:
- V12-M-01: Wrong return value → DoS entire batch
- This finding: Reverting callback → Bypass validation logic

**General Attack Pattern:**

1. User implements `IClaimRecipient` with access control/validation in `onClaim()`:

2. User sets this recipient via `setClaimRecipient()`
3. Malicious operator calls `claimWithRecipient()` with non-empty `data`
4. `onClaim()` reverts due to failed validation
5. **Empty catch block swallows the revert**
6. Claim succeeds and tokens are transferred
7. Intended validation/access control is bypassed

**Impact:**

1. **Callback Validation Bypass**: Recipients cannot reliably enforce access control or validation logic
2. **Protocol Invariant Undermined**: The callback mechanism exists to allow recipients to perform custom logic and validation, but it can be completely bypassed
3. **Silent Failures**: Recipients have no way to prevent unwanted claims if their validation logic reverts
4. **Inconsistent Behavior**: Success with wrong return value → revert; Failure with revert → success (asymmetric)

**Who Can Exploit:**
- Any operator or authorized claimer can bypass recipient validation
- Recipients cannot prevent bypass (reverts are swallowed)

**Financial Impact:**
- Depends on what logic the recipient intended to enforce
- Could enable unauthorized claims, excessive claims, or violation of custom rules
