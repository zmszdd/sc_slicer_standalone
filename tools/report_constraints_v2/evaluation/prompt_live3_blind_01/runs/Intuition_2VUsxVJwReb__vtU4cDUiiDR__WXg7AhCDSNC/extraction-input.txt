`previewWithdraw` underflows after 2 deposits on ProgressiveCurve and OffsetProgressiveCurve

## Summary

`previewWithdraw` in both curve contracts reverts after just two deposits. The deposit path floors shares via `sqrt()`, so `totalShares` ends up slightly smaller than what the curve formula expects for the accumulated `totalAssets`. When `previewWithdraw` then squares that deflated `totalShares` (rounding down) and divides `assets / HALF_SLOPE` (rounding up), the subtraction `square(s) - deduct` underflows by 1 wei.

`previewRedeem` is unaffected — it uses a different code path (`square(s) - square(sNext)`) that doesn't hit this mismatch.

## Impact

`previewWithdraw` is a core function of the bonding curve interface (`IBaseCurve`) and is publicly exposed through `BondingCurveRegistry.previewWithdraw()`. After just 2 deposits into any vault using `ProgressiveCurve`, this function permanently reverts.

MultiVault currently only uses `deposit`/`redeem` internally, so the on-chain withdraw-by-assets path doesn't exist yet. But the function is part of the bonding curve's public API and the registry explicitly wraps it for external callers. Any contract or integration that composes on top of the registry's `previewWithdraw` to build an asset-denominated withdrawal (which is the standard ERC-4626 pattern these curves are designed to support) will hit a revert. Front-ends and aggregators calling the curve or registry to preview "how many shares do I burn for X assets" also break.

The bug is deterministic — it triggers on every `ProgressiveCurve` vault after normal operation (2 deposits). It's not a corner case or a dust-amount artifact. The `OffsetProgressiveCurve` has the same code pattern and accumulates the same drift, though the OFFSET gives it more headroom before it trips.
