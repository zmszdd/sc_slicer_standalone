Share Inflation Attack in GrowthHYBR Contract

## Finding description and impact
The `GrowthHYBR` contract implements an auto-compounding vault where users deposit HYBR tokens to receive gHYBR shares. The contract internally creates and manages a single veNFT (vote-escrowed NFT) in the `VotingEscrow` contract, where all deposited HYBR is locked.

Through `GrowthHYBR::deposit()`, users deposit HYBR tokens and receive gHYBR shares proportional to their contribution. The share calculation is based on the ratio between `totalSupply()` (total gHYBR shares) and `totalAssets()` (total HYBR locked in the veNFT):


The vulnerability arises because **anyone can directly call `VotingEscrow::deposit_for()` to increase the locked amount of any veNFT**, including the one owned by `GrowthHYBR`. This allows an attacker to artificially inflate `totalAssets()` without minting corresponding gHYBR shares, enabling a share inflation attack.

## Root Cause

The root cause lies in two key factors:

1. **Public `deposit_for()` function in VotingEscrow**: The `VotingEscrow::deposit_for()` function is publicly accessible and allows anyone to add HYBR tokens to any existing veNFT:


2. **Direct dependency on veNFT balance**: The `GrowthHYBR::totalAssets()` function directly reads the locked amount from the veNFT, which includes any externally-added tokens:


This creates an exploitable path where `totalAssets` can be inflated without proportionally increasing `totalSupply`, leading to severe share dilution for subsequent depositors.

## Impact

- First depositors can be diluted to 0 shares, with their funds effectively stolen by the attacker
