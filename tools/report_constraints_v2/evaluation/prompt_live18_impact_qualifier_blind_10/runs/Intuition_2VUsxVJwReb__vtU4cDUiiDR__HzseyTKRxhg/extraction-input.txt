`ProgressiveCurve.previewWithdraw` reverts for most deposit amounts due to ceil/floor rounding mismatch

## Vulnerability details

### Root Cause

In `previewWithdraw` ([ProgressiveCurve.sol L153](https://github.com/code-423n4/2026-03-intuition/blob/main/src/protocol/curves/ProgressiveCurve.sol#L153)), `deduct` is computed with ceiling division (`PCMath.divUp`), while `PCMath.square(s)` uses floor rounding (`mul(x, x)`):


When `assets == totalAssets` (full withdrawal), the relationship `totalAssets ≈ HALF_SLOPE * totalShares²` means `deduct = ceil(totalAssets / HALF_SLOPE)` can exceed `floor(totalShares²)` by 1 ULP, causing the `sub()` to underflow and revert.

This was partially addressed in PR #136 which fixed the analogous rounding issue in `_convertToAssets` (line 240) by using consistent floor rounding. However, `previewWithdraw` was missed, it still uses `divUp`.

### Impact

`previewWithdraw` reverts with a UD60x18 underflow for the vast majority of deposit amounts. Any external integration, UI, or on-chain contract calling `BondingCurveRegistry.previewWithdraw` (which delegates to `ProgressiveCurve.previewWithdraw`) will encounter an unexpected revert when querying a full withdrawal. This breaks the public API contract where `previewWithdraw(totalAssets, totalAssets, totalShares)` should return `totalShares` for a full withdrawal, and never revert for valid inputs (`assets <= totalAssets`).

`OffsetProgressiveCurve` shares the same root cause in its `previewWithdraw` function at the same line range.

Note that the actual `redeem` path via `_convertToAssets`/`previewRedeem` is NOT affected, the protocol's core deposit/redeem flow works correctly. Only the `previewWithdraw` view function is broken.
