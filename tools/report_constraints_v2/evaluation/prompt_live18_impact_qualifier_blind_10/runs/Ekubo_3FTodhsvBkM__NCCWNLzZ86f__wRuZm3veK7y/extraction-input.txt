FlashAccountant.updateDebt() lacks locker authorization, allowing malicious ETH recipients to brick their own locks

Summary

Component
src/base/FlashAccountant.sol – updateDebt()

Issue

updateDebt() uses _getLocker() instead of _requireLocker() to obtain the active lock.
_getLocker() only checks that a lock is active.
_requireLocker() additionally enforces that msg.sender is the current locker.

Because updateDebt() is external and only uses _getLocker(), any contract that is called while a lock is active can invoke updateDebt() and inject arbitrary debt for the current lock, even though it is not the locker.

One concrete and realistic path is through native ETH withdrawals: when a locker calls withdraw() with the native token and a recipient address, the FlashAccountant does a low-level call to that recipient. If the recipient is a contract with a receive() function, that receive() runs while the lock is still active and can call updateDebt().

Injected debt increments the per-lock non-zero debt counter, so when the lock completes, the final DebtsNotZeroed check fails and the whole operation reverts.

Impact

A malicious ETH recipient contract can force any lock that pays it ETH to revert, creating a deterministic DoS for those transactions.

The attacker can:
Inject arbitrary debt values for their own “token” (their contract address).
Cause the lock to always fail its DebtsNotZeroed invariant at the end of execution.
Funds are not stolen because the entire transaction reverts, but protocol liveness for affected flows is broken.

Current reachability you demonstrate in the PoC:
The victim/locker chooses a recipient address (e.g. for a withdrawal/refund).
If that recipient is a malicious contract, it can:

Receive ETH,
Call updateDebt() inside receive(),
Brick the transaction with DebtsNotZeroed.

Because all ETH recipients in the existing code paths are user-controlled, this is currently a self-DoS / griefing of one’s own operation, not cross-user griefing.

Risk level:

Technical bug: clear authorization failure in a core accountant component.

Impact today: per-transaction DoS of flows where the user points an operation at a malicious recipient → Medium by typical C4 standards.

Root Cause

In FlashAccountant.updateDebt():
The function uses _getLocker():

function updateDebt() external {
    if (msg.data.length != 20) revert UpdateDebtMessageLength();

    // Only checks "there is an active lock"
    uint256 id = _getLocker().id();  // <-- no msg.sender == locker check

    // parse delta from calldata and account it as debt for msg.sender (token)
    _accountDebt(id, msg.sender, delta);
}


_getLocker() only ensures a lock exists; it does not verify that the caller is the current locker.

By contrast, other public entrypoints that mutate debt (e.g. withdraw()) use _requireLocker(), which does:

function _requireLocker() internal view returns (Locker locker) {
    locker = _getLocker();
    if (locker.addr() != msg.sender) revert LockerOnly();  // proper auth check
}


This inconsistency means that updateDebt() is the only debt-mutating public interface that does not enforce msg.sender == locker.addr().

As a result, any contract executed during an active lock (e.g. ETH recipient in receive()) can:

Call updateDebt().
Pass _getLocker() because a lock is active.
Modify the lock’s debt for the “token” equal to its own address (msg.sender).

The fake debt increments the lock’s non-zero debt counter, which is checked at the end of the lock, causing DebtsNotZeroed and reverting the entire transaction.
