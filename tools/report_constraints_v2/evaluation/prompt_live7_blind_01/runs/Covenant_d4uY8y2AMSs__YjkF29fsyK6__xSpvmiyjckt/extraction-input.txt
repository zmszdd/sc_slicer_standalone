Self-transfer to Covenant during base payouts desynchronizes accounting and locks funds

## Summary

The Covenant contract allows users to set the recipient address to the contract itself (`address(this)`) when redeeming tokens or swapping to base assets. This creates a vulnerability where ERC20 transfers become no-ops while internal accounting (`baseSupply`) is still decremented, permanently locking base tokens in the contract and reducing effective liquidity for all users.

## Description

In the `redeem()` and `swap()` functions, when base tokens are being paid out, the contract transfers tokens to a user-specified recipient address without validating that the recipient is not the contract itself. When a user sets the recipient to `address(this)`, the ERC20 transfer becomes a self-transfer that most standard ERC20 implementations treat as a no-op - the token balance remains unchanged. However, the contract still decrements `marketState.baseSupply` by the payout amount and any protocol fees, creating a persistent divergence between the contract's actual token balance and its internal accounting.

The vulnerability occurs in two specific code paths. In `redeem()`, the function updates `ms.baseSupply = localBaseSupply - amountOut - protocolFees` and then executes `IERC20(mp.baseToken).safeTransfer(redeemParams.to, amountOut)`. Similarly, in `swap()` when `assetOut == BASE`, the function updates `ms.baseSupply = localBaseSupply - amount - protocolFees` and executes `IERC20(mp.baseToken).safeTransfer(swapParams.to, amount)`. In both cases, if the recipient is `address(this)`, the accounting update occurs but no tokens actually leave the contract.

This behavior is inconsistent with the `collectProtocolFee()` function, which explicitly prevents self-transfers by checking `if (recipient == address(this)) revert Errors.E_Unauthorized()`. The absence of this same validation in the payout paths creates an unintended griefing vector.

## Impact Explanation

The vulnerability enables permanent locking of base tokens within the contract. Each time a self-transfer occurs, the difference between the contract's actual ERC20 balance and the tracked `baseSupply` increases by the payout amount plus any protocol fees. These excess tokens become permanently stranded since they are not reflected in the internal accounting and cannot be withdrawn through normal user flows or protocol fee collection mechanisms. The locked funds reduce the effective liquidity available to all users, as liquidity calculations rely on `baseSupply` rather than the actual token balance, potentially impairing future redemptions and degrading overall market functionality.

## Likelihood Explanation

The vulnerability can be triggered by any user simply by setting the recipient parameter to the Covenant contract address during redemption or base-out swaps. Most standard ERC20 tokens allow self-transfers without reverting, making the condition broadly applicable across different base tokens. However, materializing significant impact requires attackers to sacrifice their own redemption proceeds, as they must lock their own tokens to harm the system. While the exploit mechanism is straightforward to execute, causing substantial damage would require repeated execution with considerable capital investment.
