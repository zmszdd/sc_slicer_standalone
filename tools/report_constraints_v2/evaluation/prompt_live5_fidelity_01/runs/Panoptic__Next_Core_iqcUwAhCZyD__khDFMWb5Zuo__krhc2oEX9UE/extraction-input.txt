Incorrect Context for `calculateIOAmounts` in Force Exercise Settlement

## Summary

The `exerciseCost` function in the `RiskEngine` contract incorrectly invokes the `PanopticMath.calculateIOAmounts` library function with the `_move` parameter set to `true`. In the Panoptic protocol’s mathematical framework, the `_move` boolean serves as a contextual toggle: `true` signifies "moving into" or opening a position, while `false` signifies "moving out of" or closing a position.

Force exercise is, by definition, a closing event where an existing long position is terminated. By passing `true` instead of `false`, the system evaluates the token deltas and required collateral using the logic intended for minting/opening. This mismatch causes the protocol to calculate the wrong amounts of Token0 and Token1 to be transferred during the exercise, potentially leading to a mismatch between the exercised liquidity and the resulting pool state.

## Vulnerable Code

The vulnerability is located in the `exerciseCost` function. The library call hardcodes the incorrect context boolean.


## Impact

This issue creates a **Mathematical Accounting Discrepancy** during force exercises:

1. **Incorrect Token Deltas**: Opening and closing an option position often involve different rounding directions or fee adjustments to protect the liquidity providers. Using the "open" logic for a "close" event results in the exercisee being charged (or refunded) an incorrect amount of underlying assets.
2. **Pool Imbalance**: If the calculated IO (In/Out) amounts are incorrect, the settlement performed by the `PanopticPool` will not perfectly offset the liquidity being removed from the Uniswap V3 pool, leading to "dust" accumulation or small losses for the protocol over time.
3. **Liquidation Failures**: In extreme cases where the "open" math requires more collateral than the user has (even though they are closing a position), the force exercise transaction may revert entirely, allowing "snipable" positions to remain open and toxic to the pool.
