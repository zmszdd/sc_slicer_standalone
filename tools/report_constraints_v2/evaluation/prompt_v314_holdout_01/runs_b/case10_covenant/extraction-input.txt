# Nested multicall resets payment flag causing DOS

## Finding Description
The Covenant core batches operations via [`Covenant.multicall()`](https://github.com/code-423n4/2025-10-covenant/blob/d5ebe4461564b46cacf8a90cf11add29470ef001/src/Covenant.sol#L507-L524) and enforces ETH payment correctness at the batch level. Per [`ICovenant.multicall()`](https://github.com/code-423n4/2025-10-covenant/blob/d5ebe4461564b46cacf8a90cf11add29470ef001/src/interfaces/ICovenant.sol#L261), “Does not check msg.value received. Instead, it uses any msgValues encoded in data and sends those onwards,” with a final pre/post balance check.

Since nested calls run in the same context, an inner `multicall()` toggles the shared `_isMulticall` flag to `true` and then resets it to `false` before returning to the outer loop. This breaks the intended payment bypass for the remainder of the outer batch, making subsequent operations fail their individual `msg.value == msgValue` check in `_checkPayment()`.

The `noDelegateCall` guard does not prevent this because it only checks that delegatecall does not change `address(this)`:

https://github.com/code-423n4/2025-10-covenant/blob/d5ebe4461564b46cacf8a90cf11add29470ef001/src/libraries/NoDelegateCall.sol#L12-L15

In our case, `Address.functionDelegateCall(address(this), ...)` keeps `address(this)` unchanged, so `noDelegateCall` does not revert.

Root cause:
- The payment-bypass is controlled by a single global flag `Covenant._isMulticall`.
- Nested `multicall()` calls toggle this flag back to `false` mid-batch due to shared state and delegatecall, re-enabling per-call payment checks and causing reverts.

Highest impact scenario:
- A batch that legitimately relies on multicall semantics for per-call `msgValue` forwarding is front-loaded with a nested `multicall()` (even empty). When the inner returns, `_isMulticall == false`, so the next operations hit `_checkPayment()` and revert with `Errors.E_IncorrectPayment`.

## Impact
Medium.

- Denial-of-service on otherwise valid batched flows, preventing governance/ops batches (e.g., `updateState()`, `mint()`, `swap()`) from executing atomically as designed.
- No direct asset theft, but material protocol availability impact aligns with Medium per c4 docs

## Likelihood 
High.
