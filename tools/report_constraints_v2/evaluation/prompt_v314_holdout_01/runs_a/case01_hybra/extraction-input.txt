Missing zero-address check in VotingEscrow transfer permanently freezes funds

## Summary

An approved operator transfers a veNFT to `address(0)` because `_transferFrom` omits the zero-address guard. Ownership is set to the zero address without executing `_burn`, approvals are cleared, and `withdraw` becomes unreachable. The escrowed ERC‑20 tokens remain trapped forever.

## Finding Description

`VotingEscrow._transferFrom` asserts in NatSpec that it "Throws if `_to` is the zero address," yet the implementation lacks that require. Any owner-approved operator (via `approve` or `setApprovalForAll`) can invoke `transferFrom/safeTransferFrom` with `_to = address(0)` when the NFT is not attached or actively voted. The flow clears approvals, moves delegates, and sets `idToOwner[_tokenId] = address(0)`; it never calls `_burn`, so the underlying lock persists. Since future `withdraw` requires owner/approval, and no one owns the token, funds are irretrievable.

Behavior alignment: The implementation contradicts its own documentation and standard ERC‑721 practice about forbidding zero-address transfers. No recovery or admin path exists to withdraw after ownership becomes zero.

## Impact and Likelihood Explanation

Impact: An approved operator transfers a veNFT to the zero address and permanently prevents any withdrawal, trapping all escrowed tokens in the contract with no owner capable of satisfying `withdraw` preconditions.

Likelihood: Users frequently grant operator approvals; the transfer only requires the NFT to be unattached and not actively voted. This path executes in one transaction and requires no unusual on-chain conditions.
