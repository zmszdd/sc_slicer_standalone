Missing startTimestamp Validation Causes Permanent Fund Loss

## Summary

The `_createCampaign()` function in `DistributionCreator.sol` lacks validation for the `startTimestamp` parameter, allowing campaigns to be created with timestamps in the distant past. This results in permanent fund loss as tokens are transferred to the distributor for campaigns that can never be legitimately processed.

## Vulnerability Details

### Root Cause

The `_createCampaign()` function validates several campaign parameters but completely omits validation for `startTimestamp`:



### The Problem

When a user creates a campaign with `startTimestamp = 0` and `duration = 3600` (minimum 1 hour):

1. The campaign "ended" at Unix timestamp 3600 (January 1, 1970, 01:00:00 UTC)
2. Funds are immediately transferred to the distributor via `_pullTokens()`
3. The off-chain Merkl engine cannot process campaigns that ended decades before creation
4. There is no mechanism to cancel campaigns or recover funds

## Impact

Permanent Fund Loss: Users lose their deposited tokens with no recovery path.

This violates the core protocol invariant stated in the README:
> "Campaign creators retain full control over their pre-deposited funds"

Once funds are transferred to the distributor for an invalid campaign:
- No `cancelCampaign()` function exists
- `decreaseTokenBalance()` only works for pre-deposited balances, not funds already sent
- `recoverFees()` is governor-only and for contract balance, not user refunds
- The campaign cannot be "fixed" via `overrideCampaign()` since the end time must be in the future

Likelihood: User mistakes with timestamps are common:
- Forgetting to set `startTimestamp` (defaults to 0 in memory)
- Timezone conversion errors
- Copy-paste mistakes from test configurations
- Frontend bugs passing incorrect values
