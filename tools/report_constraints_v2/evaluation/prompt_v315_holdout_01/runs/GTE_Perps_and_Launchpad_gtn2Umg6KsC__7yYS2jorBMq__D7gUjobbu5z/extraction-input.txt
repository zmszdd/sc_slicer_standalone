Flawed rewards termination logic attempts premature ending or failure to end gracefully

## Finding description and impact
The Launchpad rewards system contains inverted termination logic that triggers opposite behaviors in each phase. Pre-bonding, it attempts to end rewards during temporary zero-share states (causing reverts or premature termination if pair exists). Post-bonding, it fails to end rewards gracefully when they should terminate, instead breaking core trading functionality.

The rewards system has backwards termination logic:


**Pre-Bonding Failure - Premature Termination:**
System incorrectly treats temporary zero-share states as completion:

1. User buys tokens during bonding (gets shares)
2. User sells back to launchpad temporarily 
3. `totalFeeShare` becomes 0 momentarily
4. System calls `_endRewards()`, permanently disabling rewards
5. **Most likely: Transaction reverts** because pair doesn't exist yet
6. **Alternative: If pair somehow exists prematurely**, rewards are permanently disabled for future participants

**Post-Bonding Failure - No Graceful Termination:**
System should cleanly end rewards when no participants remain, but instead breaks trading:

1. All participants naturally exit over time (expected behavior)
2. `totalShares` reaches 0 - **rewards should terminate gracefully here**
3. Instead of ending cleanly, system blocks `addRewards()` calls
4. AMM trading fails because fee distribution reverts
5. **Trading becomes permanently impossible** instead of rewards simply ending
