Router swaps have no deadline, so stuck transactions execute at stale prices

- **Description:** Ekubo’s Router forwards swaps to CORE.swap without reading a deadline or timestamp. SwapParameters contains no expiry value either. Once a user signs a swap transaction it remains valid indefinitely; if it lingers in the mempool and the market moves, the router can still execute it later at the stale price, violating the user’s intent. (The Starknet implementation of Ekubo already implements deadlines; the EVM router should do the same.)


- **Impact:** A swap broadcast at price P can be mined much later at price P′. The router only checks the old price limit, so the user might miss large gains or incur unexpected losses even though they never re-signed the transaction.


- **Recommendation:** Add a mandatory deadline parameter to every router entry point (single-hop, multihop, and multi-multihop). Reject swaps mined after that timestamp to align with users’ expectations and the Starknet implementation.
