Critical Accounting Drift Through Unvalidated Self-Transfers Affecting All Market Participants

** Description **

The Covenant protocol fails to validate the to parameter in three critical user-facing functions: `mint()`, `redeem()`, and `swap()`, allowing users to specify `address(this)` (the Covenant contract itself) as the `recipient`.

This causes tokens to be transferred to the contract itself while the accounting state (baseSupply) is updated as if tokens left the contract, creating a permanent accounting drift that violates the protocol's fundamental invariant and affects all users in the market, not just the attacker.

Affected Functions:

- `Covenant.redeem()`
- `Covenant.swap()` when assetOut == BASE
- `Covenant.mint()` for synthetic token minting

=> Root Cause

Step 1: Missing Validation

The protocol's validation layer (ValidationLogic.sol) checks various parameters but never validates that `to != address(this)`:

None of the validation functions (checkMintParams(), checkRedeemParams(), checkSwapParams()) include this critical check.

Step 2: State Update Before Transfer

When a user calls `redeem()` with `to = address(covenant)`:

The baseSupply is decreased, treating the operation as if tokens are leaving the contract.

Step 3: Self-Transfer

The contract then executes:


When `redeemParams.to = address(covenant)`, tokens are transferred from the contract to itself - they never actually leave.

Step 4: Accounting Invariant Broken

The fundamental invariant `contract.balanceOf(baseToken) >= baseSupply + protocolFeeGrowth` is now violated:

- Physical balance: Unchanged (tokens stayed in contract)
- Accounted balance (baseSupply + protocolFeeGrowth): Decreased
- Result: Unaccounted tokens trapped in the contract

** Impact **

-> Direct Impact

1. Accounting Drift: The protocol's baseSupply no longer accurately reflects the collateral backing synthetic tokens, breaking the core invariant.

2. Fee Extraction Beyond Earnings: The owner can call collectProtocolFee() to extract "fees" that include the unaccounted tokens, effectively stealing user funds.

3. Failed Redemptions: Legitimate users attempting to redeem may be denied due to artificially low baseSupply, even though the contract holds sufficient physical tokens.

-> Multi-User Impact

This bug affects ALL users in the market, not just the attacker:

1. Shared Market State: The baseSupply variable in marketState[marketId] is global to the entire market. When one user creates accounting drift, it corrupts the state for all subsequent users.

2. Subsequent User Losses: After the attack, innocent users may:

- Have their redemptions fail due to insufficient baseSupply
- Lose funds when the owner extracts unearned fees via collectProtocolFee()
- Be unable to access their rightful collateral

3. No User Protection: There's no way for innocent users to detect or prevent this attack before it happens. They simply interact with a corrupted market state.

=> Example Scenario:

- User A (attacker) deposits 100 ETH, mints tokens
- User A redeems 50 ETH to address(covenant) → creates 50 ETH accounting drift
- User B (innocent) deposits 60 ETH, mints tokens
- User B tries to redeem their full position
- Redemption fails because baseSupply shows only 50 ETH available, even though the contract holds 110 ETH (100 + 60 - 50 redeemed)
- Owner calls `collectProtocolFee()` and extracts the 50 ETH drift, stealing User B's funds
