Slashing Penalty Bypass because the Calculations Occurs in queueWithdrawal() function.

## Finding description and impact
In the StakingManager contract, we generally use a withdrawal delay period (7 days by default) to ensure users cannot quickly exit to avoid penalties when malicious validator behavior is detected. However, there is a critical flaw in the implementation: the HYPE amount to be returned to users is calculated at the time of queuing the withdrawal rather than at the time of confirmation.

This implementation choice creates a vulnerability where users can front-run slashing events by monitoring dafault oracle which updates every 1 hour and quickly queuing withdrawal requests before the slashing is officially reported through the oracle manager which updates the validator values every 24 hours for the protocol.

There's a timing issue between Oracle updates and OracleManager updates. The DefaultOracles can update validator metrics every hour (`MIN_UPDATE_INTERVAL = 1 hours` in DefaultOracle.sol), while OracleManager only updates validator performance data every 24 hours (`MIN_UPDATE_INTERVAL = 24 hours` in OracleManager.sol). This creates a large window where users can detect validator misbehavior (through off-chain monitoring) and front-run the on-chain slashing by queuing withdrawals.


This calculation happens when a user queues a withdrawal, not when they confirm it after the delay period. Consequently, the exchange rate used to calculate the HYPE amount is fixed at queue time, and any slashing events that occur during the 7-day waiting period will not affect this user's withdrawal amount.


## Impact

1. Users who are monitoring validators / defaultOracles can escape slashing penalties entirely by timing their withdrawals.
2. Loss for other users as they have to bear the whole slashing amount.
