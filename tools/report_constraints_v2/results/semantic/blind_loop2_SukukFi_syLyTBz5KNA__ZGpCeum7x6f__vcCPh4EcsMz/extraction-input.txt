Permanent fund lock via zero-address controller

## summary
Missing zero-address validation for the `controller` parameter in request flows allows creation of requests that no one can claim or cancel, permanently locking user assets or shares.

## Finding Description
The contract implements asynchronous request lifecycles keyed by `controller` across deposits and redeems. In `requestDeposit()` and `requestRedeem()`, the `controller` address is accepted without zero-address validation. Later claim and cancel functions authenticate strictly against `controller` (or its approved operator). If a request is created with `controller == address(0)`, there is no valid caller that can pass the `controller`-bound authentication, so the request can never transition to the Claimed state or be canceled. This results in permanent locking of funds.

- Where requests are created without validating `controller`:
  - `requestDeposit()` in `/2025-11-sukukfi/src/ERC7575VaultUpgradeable.sol:341`
  - `requestRedeem()` in `/2025-11-sukukfi/src/ERC7575VaultUpgradeable.sol:715`
- Where the authentication hard-binds to `controller`:
  - `deposit()` in `/2025-11-sukukfi/src/ERC7575VaultUpgradeable.sol:557`
  - `mint()` in `/2025-11-sukukfi/src/ERC7575VaultUpgradeable.sol:633`
  - `cancelDepositRequest()` in `/2025-11-sukukfi/src/ERC7575VaultUpgradeable.sol:1574`
  - `claimCancelDepositRequest()` in `/2025-11-sukukfi/src/ERC7575VaultUpgradeable.sol:1691`
  - `cancelRedeemRequest()` in `/2025-11-sukukfi/src/ERC7575VaultUpgradeable.sol:1745`
  - `claimCancelRedeemRequest()` in `/2025-11-sukukfi/src/ERC7575VaultUpgradeable.sol:1866`

Additionally, the zero-address is added to `activeDepositRequesters`/`activeRedeemRequesters`, polluting metrics and pagination, and reserved totals remain inflated.

Highest-impact scenario: An approved operator or owner submits `requestDeposit()` or `requestRedeem()` with `controller == address(0)`. Assets or shares are pulled into the vault and recorded under the zero-address key. Even after fulfillment, no one can call `deposit()`, `mint()`, `redeem()`, `withdraw()`, or cancel/claim cancel functions because they require `controller == msg.sender` or its approved operator. As a result, funds remain stuck indefinitely.

## Attack Path
- Step 1: Call `requestDeposit(assets, controller=0x0000000000000000000000000000000000000000, owner)` or `requestRedeem(shares, controller=0x0, owner)`.
- Step 2: Funds move into the vault; state records under `controller` key `0x0`.
- Step 3: Manager fulfills to claimable; claim functions require `controller` authentication (`controller == msg.sender` or `isOperator(controller, msg.sender)`), which cannot be satisfied for `0x0`.
- Step 4: Cancelation functions also require `controller` authentication; the `owner` cannot cancel. Funds are permanently locked.

## Impact
High. Permanent loss of access to user funds via unclaimable/un-cancelable requests and systemic state pollution; no viable recovery path without special admin intervention.

## Recommendation
Validate `controller` is non-zero on request entry points (and optionally validate `receiver` is non-zero in claim functions). If you need to support repairing misconfigured requests, provide a gated admin rescue that returns funds to the `owner` when `controller == address(0)`.
