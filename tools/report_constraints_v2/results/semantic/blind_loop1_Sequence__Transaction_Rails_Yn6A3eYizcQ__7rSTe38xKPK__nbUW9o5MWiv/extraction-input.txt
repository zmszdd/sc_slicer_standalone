delegatecall to multicall3 enables arbitrary spending of router assets

## summary
Public router multicall entrypoints in TrailsRouter delegate to Multicall3 without delegatecall-only gating or target/value constraints, allowing any EOA to run arbitrary aggregate3Value batches in the router’s context and directly spend router-held ETH and ERC‑20 balances. This results in direct theft of all assets held by the router.

## Finding Description
The TrailsRouter contract exposes three public functions—execute, pullAmountAndExecute, and pullAndExecute—that forward arbitrary IMulticall3.aggregate3Value payloads to the canonical Multicall3 via delegatecall, executing subcalls in the storage and balance context of TrailsRouter.The TrailsRouter contract exposes three public entrypoints that delegate to the canonical Multicall3 router:

- [`execute(bytes data)`](https://github.com/code-423n4/2025-11-sequence/blob/593987c2b569f3212d2cadb31fc8d14b84bc30a9/src/TrailsRouter.sol#L59-L64)
- [`pullAmountAndExecute(address token, uint256 amount, bytes data)`](https://github.com/code-423n4/2025-11-sequence/blob/593987c2b569f3212d2cadb31fc8d14b84bc30a9/src/TrailsRouter.sol#L85-L100)
- [`pullAndExecute(address token, bytes data)`](https://github.com/code-423n4/2025-11-sequence/blob/593987c2b569f3212d2cadb31fc8d14b84bc30a9/src/TrailsRouter.sol#L67-L82)

All three functions allow any external account to execute arbitrary `IMulticall3.aggregate3Value` payloads in the context of `TrailsRouter`, spending **router-held ETH and ERC‑20 balances**.

### 1. Unconstrained [`execute()`](https://github.com/code-423n4/2025-11-sequence/blob/593987c2b569f3212d2cadb31fc8d14b84bc30a9/src/TrailsRouter.sol#L59-L64) multicall

The `execute()` function is defined as:

https://github.com/code-423n4/2025-11-sequence/blob/593987c2b569f3212d2cadb31fc8d14b84bc30a9/src/TrailsRouter.sol#L59-L64

The helper [`\_validateRouterCall()`](https://github.com/code-423n4/2025-11-sequence/blob/593987c2b569f3212d2cadb31fc8d14b84bc30a9/src/TrailsRouter.sol#L373-L396) only enforces the selector is `aggregate3Value`, and each `IMulticall3.Call3Value` has `allowFailure == false`. It **does not** restrict `calls[i].target` (arbitrary address), `calls[i].value` (ETH forwarded per subcall), `calls[i].callData` (arbitrary function calls).

Because `execute()` uses `delegatecall` into `MULTICALL3`, each subcall is effectively run as:


but in the **context of `TrailsRouter`** , `msg.sender` in each subcall is `TrailsRouter`. Any `call.value` is paid from `address(this).balance` of `TrailsRouter`. Any ERC‑20 `transfer()` / `transferFrom()` invoked by `call.callData` uses `TrailsRouter`’s balances and allowances. Thus, if `TrailsRouter` holds any ETH or ERC‑20 tokens (via other flows or direct transfers), an attacker can craft an `aggregate3Value` batch where:

- One subcall transfers the router’s entire token balance to the attacker, e.g. `token.transfer(attacker, routerTokenBalance)`,
- Another subcall sends the router’s entire ETH balance to the attacker, via an empty call to the attacker address with `value = routerEthBalance`.

### 2. [`pullAmountAndExecute()`](https://github.com/code-423n4/2025-11-sequence/blob/593987c2b569f3212d2cadb31fc8d14b84bc30a9/src/TrailsRouter.sol#L85-L100) with `token == address(0)` and `amount == 0`

The `pullAmountAndExecute()` function is defined as:

https://github.com/code-423n4/2025-11-sequence/blob/593987c2b569f3212d2cadb31fc8d14b84bc30a9/src/TrailsRouter.sol#L85-L100

Key points:

- For the ETH branch (`token == address(0)`), the only condition is `msg.value < amount`.
- If an attacker calls `pullAmountAndExecute(address(0), 0, data)` with `msg.value == 0`, the check becomes `0 < 0`, which is **false**, so the function does **not** revert.
- The function then directly performs `MULTICALL3.delegatecall(data)` with no further constraints.

As with `execute()`, `aggregate3Value` subcalls can freely spend `address(this).balance` by setting `call.value`, invoke arbitrary `callData` such as `token.transfer(attacker, routerTokenBalance)`. Crucially, this gives an attacker **another public entrypoint** to perform the same router-balance-draining behavior **without providing any ETH or tokens up-front** (since `amount == 0` and `msg.value == 0` are accepted).

### 3. [`pullAndExecute()`](https://github.com/code-423n4/2025-11-sequence/blob/593987c2b569f3212d2cadb31fc8d14b84bc30a9/src/TrailsRouter.sol#L67-L82`) with ETH and dust `msg.value`

The `pullAndExecute()` function is:

https://github.com/code-423n4/2025-11-sequence/blob/593987c2b569f3212d2cadb31fc8d14b84bc30a9/src/TrailsRouter.sol#L67-L82

For the ETH branch (`token == address(0)`), it only requires `msg.value > 0`, then calls `pullAmountAndExecute(address(0), msg.value, data)`. If `TrailsRouter` already holds a large ETH balance `routerEthBalance`, an attacker can:

- Seed the router so that `address(router).balance == routerEthBalance`,
- Call `pullAndExecute(address(0), data)` with a **dust** `msg.value` (e.g. `1 wei`),
- `pullAmountAndExecute()` will accept the call (`msg.value == amount`),
- The `aggregate3Value` payload can then set `call.value = routerEthBalance + dust` and send **all ETH on the router (including the pre-existing balance)** to the attacker,
- Similarly, the payload can drain any ERC‑20 balances on the router via a `transfer` subcall.

This means a dust amount (e.g. `1 wei`) is sufficient for an attacker to unlock a powerful delegatecall that can drain arbitrarily large router-held balances.

### 4. Router balances are realistic and expected

`TrailsRouter` is explicitly designed to accept direct ETH via `receive()`:

Temporarily hold funds during flows like `pullAmountAndExecute()` and `injectSweepAndCall()` and handle cross-chain and same-chain flows where balances can remain on the router between steps.

The `FLOW.md` documentation describes scenarios where:

- `pullAndExecute()` is used for same-chain swaps via `TrailsRouterShim`,
- ETH or tokens can remain on the router after execution,
- Sweeper functions (`sweep()`, `refundAndSweep()`, `validateOpHashAndSweep()`) are protected by `onlyDelegatecall` and rely on sentinel logic.

However, `execute()`, `pullAmountAndExecute()`, and `pullAndExecute()` are **public** and can be called directly by any EOA, without delegatecall context or sentinel checks. This contradicts the intended “delegatecall-only router pattern” and exposes router-held balances as a public honeypot.



## Attack Path
- Seed router balances (ETH or ERC‑20) via any mechanism (direct `receive()` or prior flow leaving funds).
- Craft `aggregate3Value` calls:
  - Call 1: `token.transfer(attacker, routerTokenBalance)`.
  - Call 2: `attacker` address as `target` with `value = routerEthBalance`.
- Invoke one of:
  - `execute(callData)` directly.
  - `pullAmountAndExecute(address(0), 0, callData)` with `msg.value == 0`.
  - `pullAndExecute(address(0), callData)` with dust `msg.value` (e.g., `1 wei`).
- Result: All router-held ETH and tokens are transferred to attacker.

## Impact
High. The vulnerability enables direct theft of all ETH and ERC‑20 tokens held by `TrailsRouter` by any EOA, with no privileged roles required. It is cross-user: if any user or integrator leaves funds on the router (which is expected in complex flows), a separate attacker can drain them. This contradicts the intended delegatecall-only router pattern and undermines system safety.

## Likelihood Explanation
Medium. The router is explicitly designed to accept ETH and temporarily hold funds across flows. Non-zero balances on the router in production are realistic, making exploitation plausible. While the path requires crafting an `aggregate3Value` payload, this is straightforward given the public entrypoints and unrestricted `target`, `value`, and `callData`.


## Recommendation
Enforce delegatecall-only execution on dangerous entrypoints and tighten ETH branch logic:

- Add `onlyDelegatecall` to:
  - `execute()`
  - `pullAmountAndExecute()`
  - `pullAndExecute()`

- Tighten ETH branch in `pullAmountAndExecute()` to reject zero amounts when `token == address(0)`.

- Optionally gate `injectAndCall()` with `onlyDelegatecall` as it also spends router-held balances and approves tokens for arbitrary `target`.
