Malicious user can DoS the withdrawal process of the GTL token.

## Finding description and impact

On short explanation GTL is a ERC4626 token and users deposit USDC in exchange for it, an important difference is that in order to withdraw or redeem users cannot use the regular ERC4626 functions like `withdraw` or `reedem`, but will need to queue a withdrawal which is later processed by the admin.

Key points for the functions `queueWithdrawal`, `processWithdrawals` and `cancelWithdrawal`:
- the system burns the shares when processing the actual withdrawal not when queueing.
- you cannot process queue orders individually, the process starts from the earliest id in the queue list.
- only the msg.sender which placed the queue withdrawal order can cancel it.

Attack path for malicious user like Bob:
1. Bob has a particular balance of shares, he queues a withdrawal.
2. Afterwards Bob transfers his balance of shares to a second EOA.
3. Processing the withdrawal reverts on burn as Bob has zero balance of shares.
4. Processing withdrawals is bricked for everyone in the queue list.

## Recommended mitigation steps

Burn the shares when queueing the withdrawal order in `queueWithdrawal`, mint the shares back incase of a canceling a queue order in `cancelWithdrawal`.
